# C++ 面经 5 · STL 容器与底层实现

这一篇是量化开发面试里出现频率最高的一类问题：STL 容器的底层数据结构、复杂度、以及围绕它们的一堆"陷阱题"。这类题不考算法技巧，考的是你对标准库容器实现原理的理解深度。面试官往往会先问"vector 怎么扩容"，然后层层追问到"为什么不用哈希表""迭代器什么时候失效""reserve 和 resize 差在哪"。回答的关键是每次都要落到具体的数据结构（连续数组、链表、红黑树、哈希表、分段数组）上去解释复杂度和行为差异，而不是背结论。这篇覆盖 vector、list、deque、priority_queue、map/set 家族、unordered 家族、allocator 以及线程安全这几大块。

```text
1. 先确认容器的底层数据结构（连续内存 / 链表 / 树 / 哈希表 / 分段数组）。
2. 从数据结构直接推出增删查改的复杂度，不要死记表格。
3. 凡是"连续内存"的容器，就要警惕扩容/插入/删除导致的迭代器失效。
4. 凡是"基于节点"的容器，插入删除是 O(1) 局部操作，迭代器基本不失效。
5. 有序 vs 无序、红黑树 vs 哈希表，永远是一对互补选择，不是谁淘汰谁。
6. 复杂度写清楚是"最坏"还是"均摊"还是"平均"，这三者对面试官来说是不同的答案。
```

## 1. vector 的底层原理

**核心结论**：`std::vector` 的底层是一段连续内存的动态数组。它内部维护三个指针（或等价物）：指向已分配内存起始位置的指针、指向当前有效元素末尾的指针（对应 `size()`）、指向已分配内存末尾的指针（对应 `capacity()`）。因为内存连续，`operator[]` 和随机访问迭代器都是 $O(1)$；但一旦已分配的空间不够用，就必须整体搬迁。

**扩容的具体步骤**：当 `push_back` 发现 `size() == capacity()` 时，vector 会：

1. 按某个增长策略计算一个新的、更大的容量（通常是当前容量的 1.5 倍或 2 倍，具体倍数由实现决定）；
2. 在新容量上分配一块全新的连续内存；
3. 把旧内存里的所有元素**拷贝或移动**到新内存；
4. 析构旧内存里的元素，释放旧内存；
5. 在新内存尾部构造新插入的元素。

**为什么增长策略是"倍增"而不是"每次加固定量"**：这是本题最常见的追问，需要用均摊分析（amortized analysis）说清楚：

- 假设每次扩容都把容量翻倍（几何增长）。从空容器开始插入 $n$ 个元素，扩容会发生在容量为 $1, 2, 4, 8, \ldots$ 时，每次扩容要拷贝当时已有的全部元素。总拷贝成本是：

$$
1+2+4+\cdots+2^{\lceil \log_2 n\rceil} < 2n
$$

这是一个公比为 2 的等比数列求和，总和被 $O(n)$ 控制住。加上 $n$ 次本身的插入操作也是 $O(n)$，所以 $n$ 次 `push_back` 总成本是 $O(n)$，均摊到每次是 $O(1)$。

- 反过来，假设每次容量只增加一个固定的常数 $k$（线性增长）。扩容会发生在容量为 $k, 2k, 3k, \ldots$ 时，每次都要拷贝当时几乎全部的已有元素，总拷贝成本是：

$$
k+2k+3k+\cdots+\frac{n}{k}\cdot k \approx \frac{n^2}{2k}
$$

这是 $O(n^2/k)$，均摊到每次插入就退化成了 $O(n)$：增长量 $k$ 越小，退化越严重。这就是为什么标准库统一选择"按比例扩容"而不是"每次加固定量"：只有几何增长才能保证 `push_back` 的均摊复杂度是 $O(1)$。

**常见追问 / 面试陷阱**

> C++ 标准是否规定了具体的扩容倍数（1.5 倍还是 2 倍）？

不规定。标准只要求 `push_back`（以及 `emplace_back`）的均摊复杂度是 $O(1)$，具体的增长因子完全是实现细节：常见实现里 libstdc++（GCC）用 2 倍，MSVC 的实现用 1.5 倍左右。只要是某个大于 1 的固定比例，均摊分析都成立，具体数值是"空间浪费"和"拷贝次数"之间的权衡，不是标准强制的。

> 扩容时元素是拷贝还是移动？这和 noexcept 有什么关系？

vector 优先使用移动而不是拷贝来减少扩容成本，但这里有一个强异常安全保证（strong exception guarantee）的约束：如果扩容过程中某次移动操作抛出异常，vector 必须保证自己能回滚到扩容前的状态（要么全部搬完，要么状态和没扩容一样，不能出现"搬了一半"的中间状态）。移动操作一般不会真正抛异常，但如果元素类型的移动构造函数**没有标注 `noexcept`**，编译器/标准库无法在编译期确认它不会抛异常，为了保证强异常安全，vector 会退回去调用**拷贝构造函数**（前提是拷贝构造函数存在）而不是移动构造函数。只有当移动构造函数标了 `noexcept`（或者类型没有拷贝构造函数、只能移动）时，扩容才会真正使用移动语义来省下拷贝的开销。这也是为什么写自定义类型时，只要移动构造不会抛异常，就应该显式标 `noexcept`，否则 vector 扩容会悄悄退化成更贵的拷贝路径。

```text
push_back 触发扩容前:
[a][b][c][d]  size=4, capacity=4   —— 已满

扩容后 (以 2x 为例):
新内存: [a'][b'][c'][d'][ ][ ][ ][ ]   capacity=8
        （a~d 是从旧内存移动/拷贝过来的）
旧内存: 释放
```

## 2. list 的底层原理

**核心结论**：`std::list` 是一个双向链表（doubly linked list）。每个节点除了存储元素本身，还额外存两个指针：指向前一个节点的 `prev` 和指向后一个节点的 `next`。容器本身只保存指向头哨兵和尾哨兵（或首尾节点）的指针，不维护连续内存。

正因为是"基于节点"的结构，list 的插入和删除在**已知位置**（拿着迭代器）时是真正的 $O(1)$：只需要重新连接前后两个节点的指针，不需要像 vector 那样搬移后面的所有元素。但代价也很明显：

- **不支持随机访问**。list 没有 `operator[]`，也没有 `at()`。要访问第 $k$ 个元素，只能从头（或尾）开始沿指针一步步走，是 $O(k)$。
- **没有缓存局部性优势**。节点在内存里是通过 `new` 逐个分配的，物理地址往往不连续，遍历时会产生大量随机内存访问和缓存未命中（cache miss），实际运行速度经常比"理论复杂度更差"的 vector 还慢。
- **每个元素有额外的指针开销**。存一个 `int`，vector 只需要 4 字节，list 的每个节点却要额外附加两个指针（64 位系统上通常是 16 字节），内存开销显著更高。

```text
head <-> [prev|data|next] <-> [prev|data|next] <-> [prev|data|next] <-> tail
              node A                node B                node C
```

## 3. vector 与 list 比较

| 维度 | vector | list |
|---|---|---|
| 底层结构 | 连续内存数组 | 双向链表 |
| 随机访问 `operator[]` | $O(1)$ | 不支持（无此接口） |
| 头部插入/删除 | $O(n)$（要搬移后面所有元素） | $O(1)$ |
| 尾部插入/删除 | 均摊 $O(1)$ | $O(1)$ |
| 中间插入/删除（已知迭代器） | $O(n)$（搬移） | $O(1)$（但定位到该位置本身要 $O(n)$） |
| 内存开销 | 低（元素紧密排列，可能有冗余 capacity） | 高（每个节点额外两个指针） |
| 缓存局部性 | 好（连续内存，预取友好） | 差（节点分散，随机跳转） |
| 迭代器失效敏感度 | 高（扩容/插入/删除都可能使大量迭代器失效） | 低（插入不影响其他迭代器；删除只使被删元素的迭代器失效） |

**什么时候用 vector、list、deque**：

- **默认优先 vector**。绝大多数场景下，即使理论上"中间插入删除"vector 是 $O(n)$ 而 list 是 $O(1)$，实际跑起来 vector 往往依然更快，因为它的缓存局部性好，常数因子小，现代 CPU 对连续内存的预取和向量化优化效果显著。只有在容器很大、且频繁在中间或头部做插入删除的场景，list 的理论优势才能真正体现出来。
- **需要频繁在两端插入删除、且不需要随机访问**时用 list（比如实现 LRU 缓存的双向链表部分）。
- **需要频繁在两端（尤其是头部）插入删除，同时又需要类似数组的随机访问**时用 deque，它是介于两者之间的折中结构：

**deque 的底层结构**：`std::deque`（double-ended queue）不是单一连续内存块，而是"分段连续"（segmented array）：内部维护若干个固定大小的小数组（chunk/buffer），再用一个"中控数组"（map，一段连续内存，存的是指向各个 chunk 的指针）把这些小数组串起来。访问元素时先查中控数组定位到具体 chunk，再在 chunk 内部定位，因此需要两次指针解引用，比 vector 略慢，但仍然是 $O(1)$。在头部或尾部插入时，如果当前端的 chunk 还有空位，直接往里放；如果满了，只需要新分配一个 chunk 并在中控数组里登记，不需要搬移已有元素，这也是为什么 deque 的头尾插入是均摊 $O(1)$，而且比 vector 的扩容代价更低（vector 扩容要拷贝全部旧元素，deque 不用）。

```text
中控数组 map:  [ptr0][ptr1][ptr2][ptr3] ...
                 |     |     |     |
                 v     v     v     v
               chunk0 chunk1 chunk2 chunk3
              [a b c][d e f][g h i][j . .]
```

## 4. vector 中的 reserve 和 resize 的区别

**核心结论**：`reserve` 只管容量（capacity），`resize` 才管大小（size）。

- **`reserve(n)`**：请求把 capacity 至少扩大到 $n$，不改变 `size()`，不构造任何新元素，也不影响已有元素的值。如果 $n \le$ 当前 capacity，通常什么都不做。
- **`resize(n)`**：真正改变 `size()` 到 $n$。
  - 如果 $n$ 大于当前 `size()`，会在末尾**构造**新元素补足差额（默认构造，或用 `resize(n, value)` 提供的值构造/拷贝）。
  - 如果 $n$ 小于当前 `size()`，会**析构**多余的尾部元素，但一般不释放内存（capacity 不变）。

**典型用法**：如果提前知道最终大约要放多少元素，应该先 `reserve`，再用 `push_back` 逐个添加，避免扩容过程中的多次重新分配和拷贝/移动：

```cpp
std::vector<int> v;
v.reserve(100000);           // 一次性分配好内存，size 仍为 0
for (int i = 0; i < 100000; ++i) {
    v.push_back(i);           // 不会再触发任何一次重新分配
}
```

对比不 `reserve` 的写法，push_back 过程中可能触发 $O(\log n)$ 次扩容，每次都要搬移当时已有的全部元素，虽然均摊仍是 $O(1)$，但常数因子（多次内存分配、多次拷贝/移动）在明确知道目标大小时完全是可以避免的开销。

**常见追问 / 面试陷阱**：`v.resize(10)` 之后再 `push_back(x)`，`x` 会被加在第 11 个位置，而不是覆盖第 10 个。很多人误以为 resize 是"预留空位等着填"，实际上 resize 已经真实构造了这些元素，它们和 push_back 加进去的元素没有本质区别。想要"预留内存但不构造元素"应该用 `reserve`。

## 5. vector 中的 size 和 capacity 的区别

**核心结论**：`size()` 是当前容器里实际存储的元素个数；`capacity()` 是当前已分配内存能容纳的元素个数上限（在不重新分配的前提下还能再 `push_back` 多少次而不触发扩容）。两者满足：

$$
\text{capacity} \ge \text{size} \ge 0
$$

多出来的 `capacity - size` 是"预留但尚未使用"的空间。这块空间存在的原因正是第 1 节讲的均摊扩容策略：每次扩容都会多留一些余量，避免频繁重新分配。

```cpp
std::vector<int> v;
std::cout << v.size() << " " << v.capacity() << "\n"; // 0 0（典型实现）
v.push_back(1);
std::cout << v.size() << " " << v.capacity() << "\n"; // 1 1
v.push_back(2);
std::cout << v.size() << " " << v.capacity() << "\n"; // 2 2
v.push_back(3);
std::cout << v.size() << " " << v.capacity() << "\n"; // 3 4（假设 2x 增长，多留了 1 个空位）
```

具体数值随实现和增长策略不同而不同，但 `capacity >= size` 这个不等式恒成立。

## 6. vector 中 erase 方法与 algorithm 中 remove 方法的区别

这是一道非常经典的陷阱题：很多人以为 `std::remove` 会让容器变小，实际上完全不会。

**`std::remove` / `std::remove_if`**（定义在 `<algorithm>`，是通用算法，不知道也不关心具体容器类型）：它只能拿到一对迭代器 `[first, last)`，没有能力改变容器的大小（因为它根本不知道自己作用的是 vector 还是数组还是别的什么）。它做的事情是：把区间里"不需要移除"的元素依次搬（移动赋值）到区间前部，返回一个新的逻辑结尾迭代器；从这个新结尾到原来 `last` 之间的元素值变得**不确定**（是被移动过之后残留的值，通常是重复值或"已被移出"的空壳状态），但容器的 `size()` 完全没变。

**`vector::erase`**：这是容器的成员函数，知道自己在操作 vector，能够真正析构元素并把 `size()` 减小。

**erase-remove idiom**：正因为 `remove` 不改变大小，标准的做法是把两者组合使用：先用 `remove` 把要删的元素都"挤"到末尾并拿到新逻辑结尾，再用 `erase` 把 `[新结尾, 原结尾)` 这一段真正删掉：

```cpp
std::vector<int> v = {1, 2, 3, 2, 4, 2, 5};
v.erase(std::remove(v.begin(), v.end(), 2), v.end());
// v 变为 {1, 3, 4, 5}，size() 真正变成 4
```

**为什么要这样组合**：单独调用 `std::remove(v.begin(), v.end(), 2)` 之后，`v` 仍然是 7 个元素（`size()` 不变），只是前 4 个是 `{1, 3, 4, 5}`，后面 3 个值不确定。如果只做这一步就以为"删除完成了"是常见的错误。必须再调用一次 `erase` 才能把 `size()` 真正缩小、把多余元素析构掉。

**常见追问 / 面试陷阱**：`std::remove` 为什么不能直接改变容器大小？因为它是一个只操作迭代器区间的通用算法模板，对任何满足 ForwardIterator 要求的区间都适用（甚至可以作用在普通数组上），普通数组根本没有"改变大小"这个概念，所以 `remove` 从设计上不需要、也不可能承担这个职责，算法和容器的职责本来就是分开的。

## 7. 正确释放 vector 的内存：clear()、swap()、shrink_to_fit()

**核心结论**：`clear()` 只清空元素，**不释放内存**；真正释放内存有两种手段：C++11 之前用 swap 技巧，C++11 之后可以用 `shrink_to_fit()`（但它只是"非强制请求"）。

- **`clear()`**：析构容器内所有元素，`size()` 变为 0，但 `capacity()` 保持不变，之前分配的内存仍然被这个 vector 持有，没有归还给系统。这是因为 `clear` 的设计意图是"清空内容以便复用同一块内存"，避免频繁分配释放的开销。

- **swap 技巧**（C++11 之前唯一可移植的做法）：

```cpp
std::vector<int> v(10000);
// ... 使用 v，此时 capacity 可能很大 ...
std::vector<int>(v).swap(v);      // C++11 之前的写法（拷贝再 swap）
// 或者，如果只是想清空并释放：
std::vector<int>().swap(v);       // 构造一个空的临时 vector，和 v 交换内部指针
```

原理是：`std::vector<int>()` 构造一个 capacity 为 0 的临时空 vector，`swap` 交换的是两个 vector 内部的指针/大小/容量这些成员（本身是 $O(1)$ 操作），交换完之后临时对象持有了原来 `v` 的那块大内存，而 `v` 变成了空的、capacity 为 0 的状态；临时对象在语句结束时被析构，随之释放掉它持有的（原本属于 `v` 的）那块内存。

- **`shrink_to_fit()`**（C++11 引入）：语义上是直接请求把 `capacity()` 收缩到贴近当前 `size()`：

```cpp
v.clear();
v.shrink_to_fit();   // 请求释放 clear 之后残留的多余 capacity
```

**常见追问 / 面试陷阱**：`shrink_to_fit()` 是否保证一定会收缩？不保证。标准原文把它描述为一个 **non-binding request**（非绑定请求），具体是否真正重新分配、是否真的把多余内存还给系统，完全取决于实现，标准不强制。因此在对内存极度敏感、必须确保释放的场景，swap 技巧仍然是更"确定"的手段（虽然写法上更绕）。

## 8. vector 迭代器失效的情况

这是面试里最容易挖坑的一节，需要按操作类型分类讨论。

**分类一：`push_back` / `insert` 触发重新分配（扩容）时**：旧内存被整体释放，所有指向旧内存的迭代器、指针、引用**全部失效**，没有例外。

**分类二：即使没有触发重新分配**：`insert` 在插入点**之后**的元素，物理位置都要往后挪一格，所以插入点及其后面所有元素对应的迭代器都会失效（指向的不再是原来的元素，甚至可能是未定义行为，取决于实现），只有插入点**之前**的迭代器还有效。

**分类三：`erase`**：删除点位置的迭代器直接失效（该迭代器指向的元素已被销毁）；删除点**之后**的所有元素都要往前搬一格来填补空缺，所以它们对应的迭代器也全部失效；只有删除点之前的迭代器保持有效。

**经典 bug**：在遍历中调用 `erase` 后忘记更新迭代器：

```cpp
// 错误写法：erase 之后 it 已经失效，再 ++it 是未定义行为
for (auto it = v.begin(); it != v.end(); ++it) {
    if (*it == target) {
        v.erase(it);   // it 失效
        ++it;          // 对失效迭代器递增，UB
    }
}
```

**正确写法**：`erase` 会返回指向被删元素下一个位置的、仍然有效的新迭代器，用它来更新 `it`，且这一分支不再额外 `++it`：

```cpp
for (auto it = v.begin(); it != v.end(); ) {
    if (*it == target) {
        it = v.erase(it);   // erase 返回下一个有效迭代器，赋值给 it
    } else {
        ++it;
    }
}
```

**常见追问 / 面试陷阱**：`reserve` 会不会使迭代器失效？如果 `reserve` 请求的容量大于当前 capacity，会触发一次真正的重新分配，所有之前的迭代器/指针/引用都会失效；如果请求的容量不大于当前 capacity，则什么都不做，不会失效任何东西。因此 `reserve` 之后紧接着的一段操作里，只要没有再触发扩容，之前保存的迭代器仍然安全。

---

## 9. priority_queue 的底层原理

**核心结论**：`std::priority_queue` 是一个容器适配器（container adaptor），默认底层用 `std::vector` 存储数据，在其上维护一个**二叉堆**（binary heap）结构；默认是**最大堆**（大顶堆），`top()` 返回当前最大元素。

**堆的数组表示**：二叉堆是一棵完全二叉树，但不需要真的用指针存树形结构，而是直接用一段连续数组隐式表示，下标关系是：

$$
\text{parent}(i) = \left\lfloor \frac{i-1}{2} \right\rfloor,\quad
\text{left}(i) = 2i+1,\quad
\text{right}(i) = 2i+2
$$

**push（插入）**：把新元素放到数组尾部（对应完全二叉树的最后一个位置），然后执行"上浮"（sift up / up-heap）：不断和父节点比较，如果比父节点大（大顶堆）就交换，直到不再违反堆性质或到达根。每上浮一层是 $O(1)$，最多上浮树高 $O(\log n)$ 层，所以 `push` 是 $O(\log n)$。

**pop（弹出堆顶）**：把堆顶元素和数组最后一个元素交换，然后删除（弹出）最后一个位置的元素，再对新的堆顶执行"下沉"（sift down / down-heap）：不断和较大的那个子节点比较，如果比子节点小就交换，直到不再违反堆性质或到达叶子。同样是 $O(\log n)$。

**top（查看堆顶）**：直接返回数组下标 0 的元素，$O(1)$。

```text
数组: [9, 5, 8, 1, 3, 7, 2]
对应完全二叉树:
                9(0)
              /      \
           5(1)        8(2)
          /   \        /   \
       1(3)  3(4)   7(5)  2(6)
```

**自定义比较器实现小顶堆**：`priority_queue` 的完整模板签名是 `priority_queue<T, Container, Compare>`，默认 `Compare` 是 `std::less<T>`（配合内部实现，得到大顶堆）。要得到小顶堆，把比较器换成 `std::greater<T>`：

```cpp
std::priority_queue<int, std::vector<int>, std::greater<int>> minHeap;
minHeap.push(5);
minHeap.push(1);
minHeap.push(3);
std::cout << minHeap.top(); // 输出 1
```

**常见追问 / 面试陷阱**：为什么 `priority_queue` 底层默认用 `vector` 而不是 `deque` 或 `list`？堆需要按下标随机访问父子节点做比较和交换（`operator[]`），`vector` 提供 $O(1)$ 随机访问且缓存局部性好；`list` 完全不支持随机访问，不能拿来实现数组式的堆。`deque` 也支持 $O(1)$ 随机访问，理论上可以作为底层容器（标准确实允许），但一般没有必要，`vector` 是默认且最常用的选择。

## 10. STL 部分容器的实现原理总览

前面几节已经详细讲过 vector、list、deque 和 priority_queue，这里做一个总览，重点放在还没细讲的 map 与 unordered_map（下一节展开）。

| 容器 | 底层数据结构 | 是否有序 | 查找 | 插入/删除（已知位置） | 随机访问 |
|---|---|---|---|---|---|
| `vector` | 连续内存数组 | 插入顺序 | $O(n)$（无序查找） | 尾部均摊 $O(1)$；中间/头部 $O(n)$ | $O(1)$ |
| `deque` | 分段连续数组 + 中控数组 | 插入顺序 | $O(n)$ | 两端均摊 $O(1)$；中间 $O(n)$ | $O(1)$（常数因子略大于 vector） |
| `list` | 双向链表 | 插入顺序 | $O(n)$ | $O(1)$（任意已知位置） | 不支持 |
| `map` / `set` | 红黑树 | 按 key 有序 | $O(\log n)$ | $O(\log n)$ | 不支持（只能迭代器遍历） |
| `unordered_map` / `unordered_set` | 哈希表（桶 + 链地址法） | 无序 | 平均 $O(1)$，最坏 $O(n)$ | 平均 $O(1)$，最坏 $O(n)$ | 不支持 |

## 11. map、set、multiset、multimap 的底层原理与特点

**核心结论**：`map`、`set`、`multimap`、`multiset` 这四个关联容器都基于**红黑树**（red-black tree，一种自平衡二叉搜索树）实现。红黑树保证从根到任意叶子的路径长度差不超过 2 倍，从而把树高维持在 $O(\log n)$，插入、删除、查找都是 $O(\log n)$。因为是二叉搜索树，对红黑树做中序遍历（in-order traversal）天然得到按 key 排好序的序列，这也是这四个容器都自带"按 key 有序"这个性质的根源。

四者的区别：

- `map`：存 key-value 对（`std::pair<const Key, T>`），key 必须唯一。
- `set`：只存 key 本身（把 key 当作 value），key 必须唯一。
- `multimap`：存 key-value 对，允许重复 key。
- `multiset`：只存 key，允许重复 key。

**为什么 map/set 的插入删除效率比 vector 这类序列容器高**：vector 的插入删除本质是"数组中间挖一个坑或者插一个东西"，需要把坑之后的所有元素整体搬移一格，是 $O(n)$；红黑树是基于节点的结构，插入删除只需要：找到目标位置（$O(\log n)$）、重新连接相邻的几个指针、必要时做最多常数次的旋转（rotation）来恢复红黑性质。这些操作都是局部的指针操作，不涉及"搬移其他元素"，所以整体是 $O(\log n)$，比数组中间插入删除的 $O(n)$ 快得多（当 $n$ 较大时）。

**为什么 map/set 插入之后，之前保存的迭代器不会失效**（被删除的那个元素对应的迭代器除外）：因为红黑树是基于节点的结构，每个元素在插入时被分配一块独立的堆内存，此后除非这个节点本身被删除，否则它的内存地址永远不变。插入新节点、删除其他节点，甚至为了重新平衡而做的旋转操作，改变的都只是节点之间的指针连接关系，**不会移动已存在节点的物理地址**。所以指向这些节点的迭代器（本质上包裹着节点指针）、引用、指针在这些操作前后依然指向同一块内存、同一个有效元素。这和基于连续内存的 vector 形成鲜明对比：vector 一旦扩容或者中间插入删除，物理地址会整体搬迁，之前的迭代器全部失效。

**为什么 map/set 没有 `reserve`**：`reserve` 这个接口的意义建立在"提前分配一大块连续内存，后续插入的元素会依次落入这块连续内存"这个前提上，而红黑树的内存分配方式是"每插入一个元素，单独为这一个节点申请一块内存"，节点之间不要求、也不可能连续，不存在"提前批量占坑"这个概念，所以红黑树类容器没有必要也没有能力提供 `reserve`。

**当数据规模从 10000 增加到 20000，查找速度如何变化**：红黑树查找复杂度是 $O(\log n)$，以 2 为底。数据量翻倍时，树高大约只增加 1（$\log_2 20000 \approx \log_2 10000 + 1$）。也就是说数据量翻倍，查找所需的比较次数只多了大约 1 次，几乎感觉不到变慢，这正是对数复杂度最核心的优势：数据规模的指数级增长，只带来查找成本的线性级增长。

---

## 12. set 为什么用红黑树而不是哈希表

**核心结论**：`std::set` / `std::map` 按标准要求必须保持元素按 key 有序，并支持依赖有序性的操作（中序遍历得到有序序列、`lower_bound` / `upper_bound` / `equal_range` 做范围查询、按序找前驱后继）。哈希表虽然平均查找是 $O(1)$，但它的组织方式是把元素按哈希值散列到各个桶里，桶与桶之间、桶内部的元素之间都不维护任何顺序关系，因此哈希表结构上就无法高效支持"按序遍历"或"范围查询"这类操作：想要有序结果只能把所有元素取出来重新排序，那就退化成了 $O(n \log n)$，失去了哈希表本来的优势。

反过来说，如果业务场景根本不需要有序性，只想要更快的平均查找速度，标准库提供了专门为此设计的 `unordered_set` / `unordered_map`（基于哈希表）。这两条线是**互补关系，不是谁淘汰谁**：需要有序性/范围查询选红黑树家族，只需要最快的平均查找选哈希表家族。

## 13. map 与 unordered_map 对比

`hash_map` 是 SGI STL 时代的非标准扩展名字（早于 C++11 标准化），2011 年标准化之后统一使用 `unordered_map` 这个名字，两者语义基本等价，现在写新代码应该用标准名字 `unordered_map`。

| 维度 | `map` | `unordered_map` |
|---|---|---|
| 底层结构 | 红黑树 | 哈希表 + 链地址法（chaining）处理冲突 |
| 元素顺序 | 按 key 有序 | 无序 |
| 查找 | $O(\log n)$（最坏也是 $O(\log n)$） | 平均 $O(1)$，最坏 $O(n)$ |
| 插入/删除 | $O(\log n)$ | 平均 $O(1)$，最坏 $O(n)$ |
| 内存开销 | 每个节点额外存红黑树的指针和颜色位 | 额外的桶数组开销，且需要按装载因子（load factor）预留空间 |
| 是否需要哈希函数 | 不需要，只需要 key 支持 `<`（或自定义 `Compare`） | 需要，key 要么是内置可哈希类型，要么必须提供 `std::hash` 特化或自定义哈希函数对象 |
| 范围查询（`lower_bound`等） | 支持，且高效 | 不支持有意义的范围查询 |

**为什么哈希表最坏情况会退化到 $O(n)$**：哈希表的平均 $O(1)$ 依赖于"哈希函数把元素比较均匀地分散到各个桶里"这个假设。如果哈希函数设计得差，或者遇到刻意构造的攻击输入，导致大量不同的 key 被映射到同一个桶，链地址法下这个桶内部退化成了一个需要线性遍历的链表，查找、插入、删除都要遍历这条链，最坏情况下所有 $n$ 个元素都落在同一个桶里，退化成 $O(n)$。

**选择原则**：需要按 key 有序遍历、需要范围查询（比如"找到第一个大于等于 x 的 key"）时用 `map`；只关心尽快查找/插入/删除、不关心遍历顺序时用 `unordered_map`（通常平均性能更快，尤其是数据量很大时）。

---

## 14. set 与 unordered_set 对比

和上一节完全对称：`set` 基于红黑树，元素按值有序，查找/插入/删除都是 $O(\log n)$，支持 `lower_bound` / `upper_bound` 等范围操作；`unordered_set` 基于哈希表，元素无序，查找/插入/删除平均 $O(1)$、最坏 $O(n)$（原因同样是哈希冲突退化成链表遍历），不支持有意义的范围查询，需要为自定义类型提供哈希函数。

选择原则同样对称：需要有序性或范围查询用 `set`；只需要判断"是否存在"、追求尽可能快的平均速度用 `unordered_set`。

## 15. STL 容器空间配置器（allocator）

**核心结论**：STL 的设计把"数据结构的逻辑"和"内存分配的具体细节"解耦开来。每一个标准容器模板的最后一个模板参数都是一个 allocator 类型，比如：

```cpp
template <
    class T,
    class Allocator = std::allocator<T>
> class vector;
```

默认使用 `std::allocator<T>`，它内部的分配/释放通常就是对 `operator new` / `operator delete` 的封装。容器所有需要申请/归还内存的地方（vector 扩容、list/map 每次创建节点等），都不直接调用 `new`/`delete`，而是统一通过传入的 allocator 对象来完成。

这样设计的好处是：用户可以在不改变容器本身任何逻辑代码的前提下，提供一个自定义的 allocator（比如基于内存池的分配器、按特定对齐要求分配的分配器、针对小对象做优化的分配器）来替换默认的内存分配策略，从而优化特定场景下的性能（减少系统调用次数、提升缓存局部性、避免内存碎片等）。这本质上是"策略模式"（strategy pattern）在标准库层面的体现：容器负责"什么时候需要内存、需要多少",allocator 负责"内存具体怎么来、怎么还",二者通过一个统一接口解耦。

## 16. STL 线程不安全的情况

**核心结论**：C++ 标准库对容器的线程安全只给出两条基本保证，除此之外的并发访问都需要调用方自己同步（加锁）：

1. **多个线程同时对同一个容器实例做只读操作是安全的**：也就是多个线程并发调用该容器的 `const` 成员函数（比如多个线程同时读 `v[i]`、同时 `find`）不会有数据竞争。
2. **多个线程各自读写不同的容器实例是安全的**：线程 A 操作它自己的 `vector`，线程 B 操作它自己的另一个 `vector`，两者互不影响。

但标准**没有**保证以下情况的安全性：多个线程同时对**同一个**容器实例做写操作（比如两个线程同时 `push_back` 同一个 `vector`），或者一个线程在写、另一个线程同时在读同一个容器实例。这些情况下标准库内部不带任何锁或同步机制，一旦发生就是数据竞争（data race），属于未定义行为。

**典型例子**：

```cpp
std::vector<int> shared_vec;

void worker() {
    for (int i = 0; i < 1000; ++i) {
        shared_vec.push_back(i);   // 多个线程不加锁并发调用，UB
    }
}

std::thread t1(worker);
std::thread t2(worker);
t1.join();
t2.join();
```

两个线程并发调用 `push_back` 可能同时触发扩容判断、同时读写内部的 `size`/`capacity`/数据指针，导致内存损坏、`size()` 结果错误，甚至程序崩溃。正确做法是用互斥锁（`std::mutex`）保护对 `shared_vec` 的每一次写操作，或者让每个线程操作自己独立的容器，最后再合并结果。

**常见追问 / 面试陷阱**：`const` 成员函数一定线程安全吗？只要没有并发的写操作介入，多个线程并发调用同一容器的 `const` 成员函数是安全的；但只要有任意一个线程同时在做非 `const` 的写操作，即使其他线程只是"读"，标准也不再保证安全，因为写操作可能正在修改内部状态（比如扩容中途），读到的可能是不一致的中间状态。

## 快速选择题

**1. `std::vector` 的 `push_back` 在没有触发扩容时，插入到尾部的时间复杂度是？**
A. $O(\log n)$
B. $O(1)$
C. $O(n)$
D. 均摊 $O(n)$

**答案：B** — 没有触发扩容时，只是在已分配好的内存尾部直接构造一个新元素，不涉及任何搬移，是严格的 $O(1)$（均摊分析只在讨论"包含扩容的情况"时才需要）。

---

**2. C++ 标准是否规定 `vector` 扩容必须严格按 2 倍增长？**
A. 是，标准强制规定为 2 倍
B. 是，标准强制规定为 1.5 倍
C. 否，标准只要求 `push_back` 均摊 $O(1)$，具体增长因子由实现决定
D. 否，标准完全不关心 `push_back` 的复杂度

**答案：C** — 标准只保证均摊 $O(1)$ 的复杂度要求，不规定具体倍数；不同实现选择不同（如 libstdc++ 常见 2 倍，MSVC 实现常见约 1.5 倍）。

---

**3. 如果 `vector` 元素类型的移动构造函数没有标 `noexcept`，但有拷贝构造函数，扩容时会发生什么？**
A. 仍然优先用移动构造，因为移动总是更快
B. 退回去使用拷贝构造，以保证强异常安全保证
C. 编译报错
D. 直接抛出异常终止程序

**答案：B** — 为了保证扩容失败时能安全回滚（强异常安全保证），标准库对"移动构造函数可能抛异常"的类型会保守地选择拷贝而不是移动。

---

**4. `std::list` 访问第 $k$ 个元素的时间复杂度是？**
A. $O(1)$
B. $O(\log n)$
C. $O(k)$
D. list 不支持访问第 k 个元素

**答案：C** — list 没有随机访问能力，必须从头（或尾）沿指针依次走 $k$ 步，是 $O(k)$（严格说是 $O(\min(k, n-k))$，因为可以从更近的一端出发）。

---

**5. 在需要频繁两端插入删除、同时又需要类似数组的随机访问时，应该优先选哪个容器？**
A. `vector`
B. `list`
C. `deque`
D. `set`

**答案：C** — `deque` 的分段连续内存结构（多个固定大小的 chunk + 中控数组）同时提供了均摊 $O(1)$ 的两端插入删除和 $O(1)$ 的随机访问（常数因子比 vector 略大），是这个场景下的折中最优解。

---

**6. `v.reserve(100)` 之后，`v.size()` 会变成多少？**
A. 100
B. 0（不变）
C. 取决于之前的 size
D. 未定义

**答案：C** — `reserve` 只影响 `capacity()`，完全不改变 `size()`；`size()` 保持调用前的值不变。

---

**7. `std::remove(v.begin(), v.end(), value)` 执行后，`v.size()` 会发生什么变化？**
A. 变小，减少了被移除元素的个数
B. 不变
C. 变成 0
D. 变成移除后剩余元素的个数

**答案：B** — `std::remove` 是通用算法，只操作迭代器区间，没有能力也无意愿改变容器大小；它只是把要保留的元素搬到前面，返回新的逻辑结尾，`size()` 完全不变。要真正缩小容器需要配合 `erase` 使用（erase-remove idiom）。

---

**8. 下面哪种写法在遍历中删除元素是正确的？**
A. `for (auto it = v.begin(); it != v.end(); ++it) { if (*it == x) v.erase(it); }`
B. `for (auto it = v.begin(); it != v.end(); ) { if (*it == x) it = v.erase(it); else ++it; }`
C. `for (auto& e : v) { if (e == x) v.erase(&e); }`
D. 以上都正确

**答案：B** — `erase` 会使被删元素及其之后的迭代器失效，必须用 `erase` 的返回值（指向下一个有效位置的迭代器）来更新循环变量，且不能对已经因为 `erase` 而更新过的位置再额外递增。

---

**9. 想要真正把 `vector` 已分配的内存归还给系统（不只是清空元素），下面哪个操作单独使用能做到？**
A. `v.clear()`
B. `v.resize(0)`
C. `std::vector<int>().swap(v)`
D. `v.pop_back()` 直到为空

**答案：C** — `clear()` 和 `resize(0)` 都只析构元素、把 `size()` 变为 0，不释放已分配的内存；只有和一个临时空 vector 交换内部指针（swap 技巧），才能让原来的大块内存被临时对象带走并在其析构时释放。（C++11 之后 `shrink_to_fit()` 也可以尝试，但标准只说是非绑定请求，不保证一定收缩。）

---

**10. `std::priority_queue` 默认的底层容器和堆类型分别是？**
A. `list`，最小堆
B. `vector`，最大堆
C. `deque`，最小堆
D. `set`，最大堆

**答案：B** — 默认底层容器是 `vector`（需要 $O(1)$ 随机访问来做父子节点比较交换），默认比较器是 `std::less`，对应结果是最大堆（大顶堆）。

**11. `map`、`set`、`unordered_map`、`unordered_set` 中，插入操作之后原有迭代器（除被删除元素外）不会失效的是哪几个？**
A. 只有 `unordered_map`、`unordered_set`
B. 只有 `map`、`set`
C. 四个都不会失效
D. 四个都会失效

**答案：B** — `map`/`set` 基于红黑树，节点内存地址插入后不再变化，迭代器稳定；`unordered_map`/`unordered_set` 基于哈希表，插入触发**重新哈希（rehash）**时会导致桶结构重新组织，所有迭代器都可能失效（不过要注意：即使不 rehash，`unordered` 系列插入也不保证元素间的相对顺序不变，具体失效规则比 `map`/`set` 更宽松，通常要按具体标准条款判断，但绝不能笼统认为它和 `map` 一样稳定）。

**12. 数据规模从 10000 增加到 20000，`std::map` 的查找耗时大致会怎样变化？**
A. 大约增加到原来的 2 倍
B. 几乎不变，只增加极小的常数开销
C. 增加到原来的 4 倍
D. 无法预测

**答案：B** — 查找复杂度是 $O(\log n)$，数据量翻倍时树高只增加约 1（$\log_2$ 意义下），查找所需比较次数几乎不变，这正是对数复杂度的核心优势。

**13. `set` 为什么底层用红黑树而不是哈希表？**
A. 红黑树实现更简单
B. 哈希表不能保证 $O(1)$
C. `set` 需要保持元素有序并支持范围查询，哈希表结构上无法高效提供这些
D. 历史遗留原因，没有本质区别

**答案：C** — `set`/`map` 按标准要求维护 key 的有序性，支持中序遍历、`lower_bound`/`upper_bound` 等范围操作；哈希表按哈希值分布元素，不维护顺序关系，无法高效支持这些操作。不需要有序性时可以选择 `unordered_set`，两者是互补关系。

**14. 关于 `unordered_map` 的最坏情况复杂度，下面哪个说法正确？**
A. 查找永远是 $O(1)$，标准保证
B. 平均 $O(1)$，但哈希冲突严重时最坏可以退化到 $O(n)$
C. 最坏情况是 $O(\log n)$
D. `unordered_map` 没有最坏情况这一说

**答案：B** — 哈希表依赖哈希函数把元素均匀分散到各个桶；如果冲突严重（哈希函数设计差或被针对性构造攻击输入），大量元素堆积到同一个桶，链地址法下退化为链表遍历，最坏情况是 $O(n)$。
