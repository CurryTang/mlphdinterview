# 操作系统 1 · 进程与线程基础

进程和线程是操作系统面试里出现频率最高、但也最容易答得"正确却空洞"的一组概念：大多数人能背出"进程是资源分配单位，线程是调度单位"，却说不清这句话具体对应到内存布局、内核数据结构、创建开销的哪个环节。量化开发岗对这块的考察通常会往两个方向深入，一是结合实际系统设计（撮合引擎该用多进程还是多线程、行情网关崩溃了为什么不能拖垮整个交易系统），二是刨内核底层机制（`fork()` 之后父子进程的内存到底是不是复制了一份、僵尸进程为什么会占用资源）。这一讲从进程与线程的本质区别出发，讲清楚孤儿进程和僵尸进程的成因与回收机制，给出多进程与多线程的系统设计对比，最后深入 `fork()` 的写时复制（Copy-on-Write）实现细节。

```text
1. 遇到"进程和线程的区别"这类问题，先锚定一句话："进程是资源分配的基本单位，线程是 CPU 调度的基本单位"，再展开到具体资源：地址空间、文件描述符表、全局变量是进程级别的，同一进程内的线程共享这些资源；只有栈、寄存器状态（含程序计数器 PC）、线程本地存储是线程私有的。
2. 遇到僵尸进程/孤儿进程的题，先分清楚这是两个独立的概念，只是经常一起考：僵尸进程的成因是"子进程死了，父进程没来收尸"；孤儿进程的成因是"父进程先死了，子进程还活着"。孤儿进程会被过继给 init/systemd，之后正常退出不会变成僵尸；僵尸进程如果父进程一直不 wait，会一直占着进程表项，直到父进程退出后被 init/systemd 顺带回收。
3. 遇到"该用多进程还是多线程"的系统设计题，先问两个问题：要不要强隔离/强容错（要则多进程），要不要频繁共享数据且对创建/切换开销敏感（要则多线程）。二者不是非此即彼，实际系统里常见"多进程 + 每个进程内部多线程"的混合架构。
4. 遇到 `fork()` 相关的题，先想清楚"写时共享，写时复制"这条主线：`fork()` 之后子进程不会立刻物理复制父进程的地址空间，而是共享同一批物理页并把页表项标记为只读，只有真正发生写操作时才会触发缺页异常，由内核在异常处理里补一份独立的物理页副本。这也是 `fork()` 之后紧跟 `exec()` 几乎不产生额外复制开销的原因。
```

## 1. 进程与线程的区别

**核心结论**：进程（process）是操作系统进行**资源分配**的基本单位，每个进程拥有独立的虚拟地址空间、独立的文件描述符表、独立的信号处理表等一整套内核资源；线程（thread）是操作系统进行 **CPU 调度**的基本单位，同一进程内的多个线程共享该进程的地址空间、打开的文件、全局变量和静态变量，但每个线程各自拥有独立的栈、独立的寄存器状态（包括栈指针 SP 和程序计数器 PC）、独立的线程本地存储（TLS）。一个进程至少包含一个线程（主线程），线程本身不能脱离进程独立存在。

这句话的关键在于把"共享"和"私有"这两类资源具体列出来，而不是停留在口号层面：

| 同一进程内所有线程共享 | 每个线程私有 |
|---|---|
| 虚拟地址空间（代码段、数据段、堆） | 栈（stack） |
| 打开的文件描述符表 | 寄存器状态（含栈指针 SP、程序计数器 PC） |
| 全局变量、静态变量 | 线程本地存储（TLS，如 `thread_local`） |
| 信号处理方式（signal handler） | 信号掩码（部分实现下线程可有独立掩码） |
| 当前工作目录、用户/组 ID | `errno`（现代 libc 实现中是线程私有的） |

```text
                     进程地址空间（同一进程内所有线程共享）
        ┌───────────────────────────────────────────────┐
        │  代码段 (.text)          只读，所有线程共享           │
        │  数据段 (.data / .bss)   全局变量、静态变量，共享       │
        │  堆 (heap)               malloc/new 分配的内存，共享  │
        │  文件描述符表 / 打开的文件                             │
        ├───────────────────────────────────────────────┤
        │   线程1栈    │   线程2栈    │   线程3栈    │   ...     │
        │   (私有)     │   (私有)     │   (私有)     │           │
        ├───────────────────────────────────────────────┤
        │ 线程1: PC/寄存器/TLS │ 线程2: PC/寄存器/TLS │ ...       │
        └───────────────────────────────────────────────┘
```

**创建/销毁开销**：创建一个新进程（`fork()` 或 `posix_spawn`）需要内核建立一套独立的内存管理结构（页表、虚拟内存区域描述符 VMA 等）、复制或初始化文件描述符表、分配新的进程控制块（PCB），即使配合写时复制（见第 4 节）省掉了物理内存的复制，这些内核对象的建立本身仍然有明显开销。创建一个新线程（`pthread_create`）只需要在已有的地址空间里分配一块新栈、初始化寄存器状态和 TLS，不需要碰页表和地址空间，开销通常比创建进程低一到两个数量级。销毁同理：进程退出需要内核回收整个地址空间和所有内核对象，线程退出只需要回收自己的栈和线程私有结构。

**通信方式**：进程之间默认没有共享内存，通信必须借助专门的 IPC（Inter-Process Communication）机制，比如管道（pipe）、命名管道（FIFO）、共享内存段（`shm_open`/`mmap`）、消息队列、信号量、Unix domain socket 或 TCP/IP socket，这些机制大多需要显式的内核调用，数据经常要经过一次内核态到用户态的拷贝（除非用共享内存显式映射同一块物理内存）。线程之间共享同一份地址空间，可以直接通过读写同一个全局变量或堆上对象通信，不需要经过内核，但代价是必须自己处理同步问题（互斥锁、条件变量、原子操作等），一旦同步没做对就会引入数据竞争（data race）。

**崩溃隔离性**：一个线程如果发生非法访问（比如空指针解引用、栈溢出）触发的是进程级别的信号（如 `SIGSEGV`），默认行为是终止整个进程，也就是说同一进程内其他线程会被一起拖垮，因为它们共享同一个地址空间，无法在崩溃发生后继续安全运行。一个进程崩溃则完全不会波及其他进程，因为它们的地址空间彼此独立，内核会正常回收这个进程的资源，其他进程该怎么跑还怎么跑。这一点是后面第 3 节"什么时候该用多进程"的核心依据。

**常见追问 / 面试陷阱**

> 追问"线程之间到底共享不共享栈"：不共享，每个线程有自己独立的栈，这也是多线程编程里"局部变量默认线程安全，除非显式传递指针/引用给其他线程"的原因。容易混淆的地方是——栈虽然私有，但栈的地址仍然落在同一个进程地址空间里，理论上其他线程只要拿到某个线程栈上变量的地址（比如通过传参传递了局部变量的指针），依然可以越权访问，这是经典的"返回局部变量地址"类 bug 在多线程场景下的变种。

> 追问"进程和线程哪个是调度实体，哪个不是"：容易被问反。现代操作系统里真正被调度器（CFS 等）挑选上 CPU 运行的是线程（准确说是内核里的任务/task，Linux 内核甚至不专门区分进程和线程，二者都用 `task_struct` 表示，区别只在于是否共享地址空间等资源），进程本身不参与调度，只是线程的资源容器。回答"进程是调度单位"是常见的错误表述。

## 2. 孤儿进程与僵尸进程

**核心结论**：僵尸进程（zombie）和孤儿进程（orphan）是两种不同触发条件的现象，僵尸进程本质是"子进程退出了但没人来收尸"，孤儿进程本质是"父进程先于子进程退出"，两者不是同一件事，也不构成因果关系——孤儿进程恰恰因为会被自动收养和回收，通常**不会**变成僵尸进程。

**僵尸进程（zombie）**：子进程调用 `exit()`（或被信号终止）后，内核会立刻回收它占用的大部分资源——内存、打开的文件描述符、地址空间等，但不会立刻销毁这个进程在内核里的进程表项，而是把该表项转换成一个"僵尸态"（状态码 `Z`），只保留最小一份信息：PID、退出状态码、资源使用统计（如 CPU 时间）。内核这样做的目的是让父进程之后调用 `wait()`/`waitpid()` 时能读到子进程的退出状态，如果子进程一退出就把表项彻底清空，父进程将永远无法知道子进程是正常退出还是被信号杀死、退出码是多少。父进程调用 `wait()`/`waitpid()` 成功读取退出状态后，内核才真正释放这个进程表项，此时 PID 才被系统回收，可以分配给新进程使用。

需要澄清的一点是僵尸进程本身**不占用实际的内存或 CPU 资源**（它已经不再运行，也没有用户态/内核态的地址空间），但它确实占用一个有限的资源：**进程表项，也就是一个 PID 槽位**。Linux 系统里 PID 的可用数量是有上限的（受 `/proc/sys/kernel/pid_max` 限制），如果父进程一直不调用 `wait()`，大量僵尸进程堆积会耗尽可用 PID，导致系统无法创建新进程，这是僵尸进程真正的危害所在。

```text
子进程调用 exit() / 被信号终止
        │
        ▼
内核回收该进程的内存、文件描述符等运行时资源
        │
        ▼
保留最小 PCB 信息（PID、退出码、资源使用统计）→ 进程状态变为 Z（僵尸）
        │
        │  此时子进程占用一个进程表项(PID)，但不占用内存/CPU
        ▼
父进程调用 wait() / waitpid() 读取退出状态
        │
        ▼
内核释放该进程表项，PID 被系统回收，可复用给新进程
```

**孤儿进程（orphan）**：如果父进程在子进程退出之前自己先退出了，子进程会失去原来的父进程。内核会把这些失去父进程的子进程重新挂载（reparent）到 `init` 进程（传统上是 PID 1）或者现代 Linux 发行版里的 `systemd` 名下。`init`/`systemd` 被设计为专门负责收养这些孤儿进程：一旦被收养的子进程退出，`init`/`systemd` 会自动调用 `wait()` 读取其退出状态并回收对应的进程表项。因此孤儿进程本身**不会**变成僵尸进程——即使原来的父进程从未打算 `wait` 它，养父进程也会替它完成这最后一步。

```text
初始状态:
  父进程(PID 100) ──fork()──▶ 子进程(PID 200)

父进程先于子进程退出:
  父进程(PID 100) 已终止
       │
       │  内核检测到 PID 200 的父进程已经不存在
       ▼
  子进程(PID 200) 被重新挂到 init/systemd(PID 1) 名下 → 此时称为孤儿进程
       │
       │  子进程后续正常退出
       ▼
  init/systemd 自动调用 wait() 回收 PID 200 的退出状态
  → 孤儿进程不会残留为僵尸进程
```

从 Linux 3.4 开始，内核还提供了 `prctl(PR_SET_CHILD_SUBREAPER)` 机制，允许任意进程声明"我要收养我这棵进程树下的孤儿"，而不必都交给 PID 1。Docker、containerd、以及 Chrome 这类会 fork 大量子进程的程序，经常用这个机制让自己（或者一个专门的 init 层，比如 `tini`）成为子树内的"子收割者"（subreaper），避免所有孤儿都涌向系统级的 `init`/`systemd`。

**如何避免僵尸进程堆积**：核心原则是父进程必须主动回收子进程的退出状态，常见做法有三种。第一种是父进程同步阻塞调用 `wait()`/`waitpid()`：

```c
#include <sys/wait.h>
#include <unistd.h>

pid_t pid = fork();
if (pid == 0) {
    // 子进程逻辑
    _exit(0);
} else if (pid > 0) {
    int status;
    waitpid(pid, &status, 0); // 阻塞等待子进程退出并回收其进程表项
}
```

第二种是注册 `SIGCHLD` 信号处理函数，在子进程退出时被异步通知，用非阻塞的 `WNOHANG` 循环回收所有已退出的子进程（避免信号合并导致漏掉某些子进程）：

```c
#include <signal.h>
#include <sys/wait.h>

void sigchld_handler(int sig) {
    // 一次 SIGCHLD 可能对应多个子进程退出（信号不排队），
    // 必须循环 waitpid 直到没有已退出但未回收的子进程为止
    while (waitpid(-1, NULL, WNOHANG) > 0) {}
}

int main() {
    signal(SIGCHLD, sigchld_handler);
    // ... fork 若干子进程 ...
}
```

第三种是"双重 fork"（double fork），常用于编写守护进程：父进程 fork 出子进程后立刻对子进程 `wait`，子进程再 fork 出孙子进程后自己立刻退出，孙子进程因为父进程（即原来的子进程）已经退出，会被立刻过继给 `init`/`systemd`，之后正常退出时由养父进程自动回收，原始父进程不需要关心孙子进程的生命周期：

```c
pid_t pid = fork();
if (pid == 0) {
    pid_t pid2 = fork();
    if (pid2 == 0) {
        // 孙子进程：会被立即过继给 init/systemd，执行真正的后台任务
        run_daemon_work();
        _exit(0);
    }
    _exit(0); // 中间这层子进程立刻退出，触发孙子进程被过继
}
waitpid(pid, NULL, 0); // 父进程只需要回收中间这一层，不用管孙子进程
```

**常见追问 / 面试陷阱**

> 追问"僵尸进程能不能用 `kill -9` 杀掉"：不能。僵尸进程已经终止运行，没有可以被信号打断的执行体，`kill` 对一个已经死亡的进程没有意义。唯一的解决办法是让它的父进程调用 `wait()`，或者等父进程自己退出后由 `init`/`systemd` 代为回收——如果父进程还活着但拒绝 `wait`（比如程序有 bug 或者被设计成故意忽略子进程状态），只能修复父进程或者直接杀掉父进程逼迫僵尸进程被过继回收。

> 追问"忽略 `SIGCHLD` 信号（`signal(SIGCHLD, SIG_IGN)`）会怎样"：在符合 POSIX 语义的现代系统（包括 Linux）上，显式将 `SIGCHLD` 设置为 `SIG_IGN` 会让内核在子进程退出时自动回收其资源，不再产生僵尸进程，父进程也无法再通过 `wait()` 取得子进程的退出状态（会立即返回 `-1` 并设置 `errno` 为 `ECHILD`）。这是一个历史遗留但仍然生效的行为，很多守护进程/服务框架用这一招简化子进程管理，代价是主动放弃了获取子进程退出码的能力。

## 3. 多线程与多进程比较

**核心结论**：多进程和多线程不是"哪个更好"的问题，而是在隔离性、开销、通信复杂度之间做取舍，实际系统设计里经常两者结合——用多进程做粗粒度的隔离边界，每个进程内部再用多线程做细粒度的并行。

| 维度 | 多进程 | 多线程 |
|---|---|---|
| 内存隔离程度 | 完全隔离，各自独立的虚拟地址空间 | 同一地址空间，隔离性弱，线程间可直接互相读写内存 |
| 创建/切换开销 | 较大：需要建立独立页表、VMA、文件描述符表等内核对象 | 较小：共享地址空间，只需分配新栈、初始化寄存器和 TLS |
| 通信复杂度 | 高：需要专门 IPC（管道、共享内存、socket、消息队列等） | 低：可直接读写共享变量，但需要自己处理同步（锁、原子操作） |
| 崩溃隔离性 | 强：一个进程崩溃不会影响其他进程 | 弱：一个线程崩溃（如非法访存）通常触发信号，拖垮整个进程 |
| 编程复杂度 | 相对较低：天然隔离，较少出现数据竞争类 bug | 较高：需要正确使用同步原语，容易出现死锁、竞争条件、false sharing |
| 上下文切换成本 | 高：需要切换页表（可能导致 TLB 刷新） | 低：同进程内线程切换通常不需要切换页表 |
| 典型适用场景 | 需要强隔离/强容错：浏览器多标签页、微服务架构、沙箱执行不可信代码 | 需要频繁共享数据、对创建/切换开销敏感：高频交易撮合引擎、并行计算、Web 服务器的连接处理 |

**选择依据**：如果业务场景要求强隔离性和容错能力——某个子任务崩溃绝不能影响系统其他部分——应该优先选多进程。经典例子是 Chrome 浏览器的多进程架构，每个标签页（在默认策略下）运行在独立的渲染进程里，一个标签页因为网页脚本触发崩溃只会导致那一个标签页失效，浏览器主进程和其他标签页完全不受影响；如果 Chrome 用单进程多线程实现所有标签页，一个标签页的渲染线程崩溃会直接拖垮整个浏览器。反过来，如果业务场景需要频繁共享大量数据（比如一个内存中的订单簿需要被多个撮合逻辑线程同时读取），且对创建/切换/通信开销高度敏感（微秒级延迟要求下，进程间 IPC 的一次上下文切换加数据拷贝可能就是几微秒的额外延迟，是不可接受的），应该优先选多线程，把同步开销通过精心设计的锁粒度或无锁结构降到最低。

实际系统里更常见的是混合架构：用多进程划分故障域和权限边界（比如行情接入、风控、订单路由分别是独立进程，一个模块挂了不影响其他模块），每个进程内部再用多线程处理该模块内部对延迟敏感、需要共享状态的并行任务。

**常见追问 / 面试陷阱**

> 追问"多线程程序里一个线程死循环占满 CPU 会怎样"：会影响同进程内其他线程的调度机会（操作系统按线程做时间片分配，这个线程会挤占本该分给同进程或其他进程线程的 CPU 时间），但不会导致其他线程崩溃或者数据错乱，这和"线程崩溃拖垮整个进程"是两回事——前者是调度资源被抢占的性能问题，后者是地址空间共享导致的正确性/存活性问题。

## 4. fork 的底层机制：读时共享，写时复制（Copy-on-Write）

**核心结论**：`fork()` 创建子进程时，内核并不会立即把父进程的整个虚拟地址空间对应的物理页复制一份给子进程，而是让子进程的页表项直接指向和父进程完全相同的物理页，并把这些共享页面的页表项统一标记为**只读**。只有当父进程或子进程中任意一方尝试写入某个共享页面时，才会触发一次缺页异常（page fault），由内核在异常处理程序里为发起写操作的一方分配一份独立的物理页副本、把原页面内容复制过去，再更新页表项使其指向新页面并恢复可写权限。这套"先共享只读、写入时才复制"的机制就是写时复制（Copy-on-Write，COW）。

**思路**：这么设计的原因是工程上的成本权衡。如果 `fork()` 老老实实把父进程占用的全部物理内存复制一份给子进程，当父进程占用内存很大（比如几个 GB）时，一次 `fork()` 的开销会非常可观；而实际使用中 `fork()` 之后紧跟一次 `exec()`（用新程序替换掉整个地址空间）是极常见的模式——`exec()` 一旦执行，子进程刚才继承来的地址空间会被整体丢弃，之前如果做了整体复制，这些复制工作全部白费。COW 把复制推迟到真正发生写操作的那一刻才做，如果子进程 `fork()` 之后立刻 `exec()`，中间几乎不会对继承来的页面做任何写入，也就几乎不产生任何物理内存复制，`fork()` 的开销被压到只剩下建立页表映射本身的成本。

```text
阶段 1：fork() 刚发生，父子进程共享同一批物理页，全部标记为只读

  父进程页表 ──┐
              ├──▶ 物理页 P（只读，被 2 个页表项引用）
  子进程页表 ──┘

阶段 2：子进程尝试写入该页 → 触发缺页异常（page fault），陷入内核

  父进程页表 ────────────▶ 物理页 P（只读）
  子进程写入触发缺页异常
        │
        ▼
  内核分配新物理页 P'，把 P 的内容复制到 P'
        │
        ▼
  子进程页表 ──▶ 物理页 P'（可写，子进程独占）

阶段 3：之后双方各自读写自己的物理页副本，互不影响

  父进程页表 ──▶ 物理页 P   （父进程独占，此时若也无其他引用者，恢复为可写）
  子进程页表 ──▶ 物理页 P'  （子进程独占，可写）
```

内核判断"是否需要真正复制"的依据是该物理页当前的**引用计数**：`fork()` 刚发生时一个共享物理页被父、子两份页表项引用，引用计数为 2；当其中一方触发写时缺页异常时，内核检查引用计数——如果大于 1（说明确实还有其他进程在共享这页），才分配新页、复制内容、更新写入方的页表项，并把原页面的引用计数减一；如果引用计数已经等于 1（说明另一方已经提前完成了自己的那次复制，或者本来就没有其他共享者），内核可以直接原地把这个页面标记为可写，不需要再复制一次。这个基于引用计数的判断是 COW 避免"重复劳动"的关键细节，也是这类问题里容易被忽略的一点。

```c
pid_t pid = fork();
if (pid == 0) {
    // 子进程：此刻和父进程共享全部物理页（只读），fork() 本身没有产生任何数据复制
    child_local_counter = 42; // 触发一次缺页异常，内核才真正为这一页分配独立物理内存
    // ... 子进程后续逻辑，通常紧跟 exec() 替换掉整个地址空间 ...
    execve("/path/to/program", argv, envp);
} else if (pid > 0) {
    // 父进程：继续使用自己视角下的地址空间，不受子进程写操作影响
    waitpid(pid, NULL, 0);
}
```

**常见追问 / 面试陷阱**

> 追问"`fork()` 之后子进程栈上的局部变量是不是和父进程共享同一份内存"：从物理页的角度看，`fork()` 刚返回的那一刻，父子进程的栈所在的物理页确实是共享的（只读），但这是实现细节，不代表语义上共享——只要任意一方对栈上的局部变量赋值（几乎立刻就会发生，比如函数调用、变量声明初始化），就会触发 COW，各自拿到独立副本。从编程模型的角度，`fork()` 之后父子进程的所有内存在逻辑上都应该被当作各自独立、互不影响的两份来看待，COW 只是内核为了性能做的底层优化，不应该也不能被应用层代码依赖或感知。

> 追问"`vfork()` 和 `fork()` 有什么区别，为什么现在不推荐用 `vfork()`"：`vfork()` 比 COW 更激进——它甚至不复制父进程的页表，子进程直接借用父进程的地址空间运行，并且会挂起父进程直到子进程调用 `exec()` 或退出为止。这在 `fork()` 之后立刻 `exec()` 的场景下比 COW 更快（连页表都不用建），但代价是子进程在 `exec()` 之前对地址空间的任何写入都会直接体现在父进程上，一旦子进程在 `exec()` 之前的代码里不小心修改了共享状态或提前返回，会导致未定义行为。现代系统里 COW 版本的 `fork()` 性能已经足够好，`vfork()`/`posix_spawn()` 通常只在对性能极度敏感且能保证子进程逻辑绝对简单（几乎立即 `exec()`）的场景下才会被考虑。

> 追问"写时复制只用在 `fork()` 上吗"：不是，COW 是一种通用的延迟复制思想，除了 `fork()`，`mmap()` 映射的私有只写文件（`MAP_PRIVATE`）、某些语言运行时的字符串/容器实现（比如老版本的写时复制字符串）、虚拟机/容器的内存快照（如 Firecracker microVM 的内存快照恢复）也会用同样的机制：先共享只读，等真正发生写入才按需复制，核心目的都是把复制开销推迟到真正需要、且只针对真正被写入的那部分数据。

## 快速选择题

1. 下列关于进程和线程的说法，最准确的是：

   A. 进程是 CPU 调度的基本单位，线程是资源分配的基本单位
   B. 进程是资源分配的基本单位，线程是 CPU 调度的基本单位
   C. 进程和线程完全等价，只是叫法不同
   D. 一个线程可以脱离进程独立存在

   **答案：B** — 进程持有独立的地址空间、文件描述符表等资源，是资源分配的基本单位；真正被调度器挑选上 CPU 运行的是线程（Linux 内核里线程和进程统一用 `task_struct` 表示）。D 错误，线程必须依附于某个进程，进程至少包含一个（主）线程。

2. 同一进程内的多个线程之间，下列哪一项是**线程私有**、不会被其他线程共享的？

   A. 全局变量
   B. 打开的文件描述符
   C. 栈（stack）与寄存器状态（含程序计数器 PC）
   D. 堆上分配的内存

   **答案：C** — 栈和寄存器状态（含 PC、SP）是每个线程独有的，这是线程能够独立执行不同代码路径的前提；全局变量、堆内存、文件描述符表都属于进程级资源，同一进程内所有线程共享。

3. 关于僵尸进程（zombie），下列说法正确的是：

   A. 僵尸进程会持续占用较多的内存和 CPU 资源
   B. 僵尸进程已经释放了内存等运行时资源，但仍然占用一个进程表项（PID 槽位），直到父进程调用 wait 回收
   C. 僵尸进程可以用 `kill -9` 强制终止并立即释放其进程表项
   D. 僵尸进程是父进程先于子进程退出导致的

   **答案：B** — 子进程退出后内核已回收其内存、文件描述符等资源，只保留 PID、退出码等最小信息等待父进程 `wait`；这期间僵尸进程占用一个进程表项(PID)。A 错误，僵尸进程不占用实际内存/CPU；C 错误，僵尸进程已经终止，无法被信号杀死；D 描述的是孤儿进程的成因，不是僵尸进程。

4. 孤儿进程（orphan）指的是：

   A. 子进程退出但父进程没有调用 wait 回收
   B. 父进程先于子进程退出，子进程被重新过继给 init/systemd 等进程
   C. 从未被 fork 创建、凭空出现的进程
   D. 因为资源不足而被内核强制杀死的进程

   **答案：B** — 孤儿进程的成因是父进程先退出，子进程失去原父进程后被内核重新挂载到 init（PID 1）或 systemd 名下。A 描述的是僵尸进程的成因。

5. 孤儿进程正常退出后，通常**不会**变成僵尸进程，原因是：

   A. 孤儿进程退出时内核会直接跳过僵尸状态
   B. 孤儿进程没有 PID，不受进程表项限制
   C. 收养孤儿进程的 init/systemd（或声明了 PR_SET_CHILD_SUBREAPER 的子收割者）会自动调用 wait 回收其退出状态
   D. 孤儿进程本质上是内核线程，不遵循普通进程的回收规则

   **答案：C** — init/systemd 被专门设计为会对其收养的所有子进程调用 `wait()`，因此孤儿进程退出后能被及时回收，不会长期停留在僵尸状态。

6. 下列哪种做法**不能**有效避免僵尸进程堆积？

   A. 父进程调用 `waitpid()` 阻塞等待子进程退出
   B. 父进程注册 `SIGCHLD` 处理函数，用 `waitpid(-1, NULL, WNOHANG)` 循环回收
   C. 使用双重 fork，让孙子进程被过继给 init/systemd 自动回收
   D. 父进程 fork 出子进程后完全不管，指望系统会自动定期清理所有僵尸进程

   **答案：D** — 只要父进程仍然存活且从不调用 `wait`，僵尸进程会一直保留，不存在系统"自动定期清理"活着的父进程名下僵尸子进程的机制；A、B、C 都是标准的有效做法。

7. 下列关于多进程与多线程对比的说法，最准确的是：

   A. 多线程的创建和上下文切换开销通常低于多进程，因为共享地址空间不需要切换页表
   B. 多进程之间可以直接共享全局变量，不需要专门的 IPC 机制
   C. 多线程环境下一个线程崩溃完全不会影响同一进程内的其他线程
   D. 多进程的通信开销总是低于多线程

   **答案：A** — 线程切换通常不涉及页表切换（TLB 不需要刷新），开销比进程切换低；B 错误，进程间默认地址空间隔离，需要专门 IPC；C 错误，线程共享地址空间，一个线程的非法访存等崩溃通常会终止整个进程；D 错误，多进程通信需要经过内核态 IPC，开销通常高于线程间直接共享内存。

8. Chrome 浏览器给每个标签页分配独立渲染进程（而不是同进程多线程）的核心原因是：

   A. 多进程比多线程创建开销更低
   B. 为了获得更强的崩溃隔离性：一个标签页崩溃不会影响浏览器主进程和其他标签页
   C. 多进程之间可以直接共享内存，不需要 IPC
   D. 因为线程无法访问网络资源

   **答案：B** — 这是多进程架构在容错性上的典型应用：地址空间彼此隔离，一个渲染进程崩溃只影响该进程本身，其他标签页和浏览器主进程不受影响；A 与事实相反，多线程创建开销通常更低。

9. `fork()` 创建子进程时，关于地址空间的处理，下列说法最准确的是：

   A. 内核立刻把父进程的全部物理内存复制一份给子进程
   B. 子进程的页表项直接指向和父进程相同的物理页，并标记为只读，只有发生写操作时才真正复制
   C. 父子进程从 fork() 开始就使用完全独立、互不共享的物理内存
   D. fork() 不会创建任何新的页表项，子进程和父进程使用完全相同的页表

   **答案：B** — 这正是写时复制（COW）机制：fork() 之后父子共享只读物理页，写操作触发缺页异常时内核才分配独立物理页副本。A 是没有 COW 优化的朴素实现，现代系统不这样做；D 错误，子进程有自己独立的页表，只是页表项指向的物理页初始时和父进程相同。

10. 关于 COW 机制中缺页异常（page fault）触发后的处理，下列说法正确的是：

    A. 内核发现是写时复制导致的缺页后，会终止发起写操作的进程
    B. 内核分配一份新的物理页，把原页面内容复制过去，更新发起写操作一方的页表项使其指向新页面并恢复可写
    C. 缺页异常只会发生在子进程写入时，父进程写入不会触发缺页
    D. 复制发生后，原来的物理页会被立即释放，不管另一方是否还在使用

    **答案：B** — 这是 COW 缺页处理的标准流程；A 错误，这是正常的、预期内的缺页，不是错误；C 错误，父子进程双方谁先写入都会触发缺页；D 错误，只有当引用计数降为 0（不再被任何进程页表引用）时原物理页才会被释放。

11. `fork()` 之后紧跟一次 `exec()` 是常见模式，写时复制机制在这个场景下的价值主要体现在：

    A. exec() 会主动关闭 COW，所以这个场景下 COW 没有意义
    B. 由于 exec() 会整体替换掉子进程继承来的地址空间，子进程在 exec() 前几乎不会写入继承的页面，COW 使得这次 fork() 几乎不产生实际的物理内存复制
    C. exec() 之后父进程的内存会被自动清空
    D. COW 只对可执行文件的代码段生效，对堆和栈无效

    **答案：B** — 如果不采用 COW，fork() 会先花费大量时间物理复制父进程的整个地址空间，而这些复制内容在紧接着的 exec() 中会被整体丢弃，纯属浪费；COW 把复制推迟到真正发生写入才做，配合 fork()+exec() 模式几乎不产生额外复制开销，这也是 COW 设计的主要动机之一。

12. 关于 `vfork()` 与标准 `fork()`（COW 实现）的区别，下列说法正确的是：

    A. vfork() 会为子进程复制一份独立页表，fork() 反而不会
    B. vfork() 让子进程直接借用父进程的地址空间运行并挂起父进程直到子进程 exec/退出，比 COW 更激进，但要求子进程在此之前不能修改共享状态
    C. vfork() 和 fork() 在现代 Linux 上性能完全相同，没有区别
    D. vfork() 是 COW 机制在多核系统上的别名

    **答案：B** — vfork() 连页表都不新建，子进程直接共享父进程的地址空间运行，因此比 COW 更快也更危险：子进程在 exec() 之前对内存的任何写入都会直接影响父进程，一旦操作不当会导致未定义行为，因此现代实践中除非极端追求性能且子进程逻辑极简单，通常优先使用 COW 版本的 fork()。
