# C++ 面经 1 · 面向对象基础与类设计

这一讲覆盖量化开发岗 C++ 面试里最基础也最容易问出深度的一类问题：类设计。封装、继承、多态是语言给出的三个抽象工具，访问权限和 `friend` 决定这些工具的边界怎么划，六大默认成员函数（以及 C++11 加入的移动语义）决定一个类的对象在拷贝、移动、销毁时到底发生了什么。这些话题表面上分散，实际上都在回答同一个问题：一个 C++ 对象的生命周期和资源所有权是怎么被语言规则管起来的。面试官喜欢从"空类有几个函数"这种小切口问起，一路问到"`vector` 扩容为什么有时候用拷贝有时候用移动"，考的是对这套规则链条的掌握程度，而不是某个孤立知识点。

```text
1. 涉及继承和访问权限的题，先分清"成员本身的访问级别"和"继承方式带来的访问级别下降"这两件事，不要混在一起判断。
2. 涉及类的行为（拷贝、赋值、析构）的题，先问自己：这个类管理堆内存/文件句柄/锁这类资源吗？管理资源的类几乎总要自己写拷贝控制成员，遵守 Rule of Three/Five/Zero。
3. 区分"拷贝构造函数被调用"（初始化，等号左边是全新对象）和"拷贝赋值运算符被调用"（对已存在对象赋值），看的是等号左边的对象是不是刚被定义出来。
4. 遇到"某个特殊成员函数会不会被隐式删除"的题，检查三处：成员里有没有引用/const/不可拷贝或不可移动的类型；基类是否把对应函数标成 private 或 `= delete`；类自己有没有显式声明了会抑制其他函数隐式生成的函数（比如声明了移动构造会连带删除拷贝构造）。
5. 遇到内存布局/性能类问题（空类大小、EBO、拷贝 vs 移动的代价），先画出对象的内存示意图，再回答问题。
```

## 1. 面向对象三大特性：封装、继承、多态

**核心结论**：封装、继承、多态解决的是三个不同层次的问题：封装管"数据和实现细节要不要暴露"，继承管"新类型怎么复用已有类型的结构和行为"，多态管"调用同一个接口时，具体执行哪段代码由运行时的对象类型决定，而不是由代码里写的静态类型决定"。三者缺一不可：只有封装，类之间没有复用关系，代码会大量重复；只有封装加继承，没有多态，调用方就必须在编译期知道每个对象的具体类型，写一堆 `if/else` 或者 `switch` 去分发，这正是面向对象想消除的东西。

**封装**指的是把数据成员和内部实现细节隐藏起来，只通过定义好的公共接口对外暴露。它解决的问题是让类的实现可以自由修改而不影响使用方。只要公共接口的语义不变，内部换一种数据结构、换一种算法都不会波及调用代码。

```cpp
class BankAccount {
public:
    explicit BankAccount(double balance) : balance_(balance) {}

    void deposit(double amount) {
        if (amount > 0) balance_ += amount;
    }

    bool withdraw(double amount) {
        if (amount <= 0 || amount > balance_) return false;
        balance_ -= amount;
        return true;
    }

    double balance() const { return balance_; }

private:
    double balance_; // 外部无法绕过 withdraw 直接把余额改成负数
};
```

如果 `balance_` 是 `public`，任何外部代码都可以绕过校验直接把余额改成负数；封装把"余额不能为负"这条不变量的维护责任收拢到类内部。

**继承**表达"是一种"（is-a）关系，让派生类复用基类已经定义好的数据成员和成员函数，并且可以新增或覆盖行为。

```cpp
class Shape {
public:
    virtual double area() const = 0;
    virtual ~Shape() = default;
};

class Circle : public Shape {
public:
    explicit Circle(double r) : r_(r) {}
    double area() const override { return 3.14159265358979 * r_ * r_; }

private:
    double r_;
};
```

继承解决的是结构和接口的复用问题：`Circle`、`Rectangle` 等都不需要重新声明"有一个 `area()` 接口"这件事。但继承本身并不提供"调用 `area()` 时自动执行正确版本"的能力，那是多态的职责。

**多态**指同一段调用代码（同一个函数签名、同一个调用点）在运行时根据对象的实际类型执行不同的实现。C++ 里的运行时多态通过虚函数和基类指针/引用实现：

```cpp
void printArea(const Shape& s) {
    std::cout << s.area() << std::endl; // 具体调用哪个 area() 在运行时决定
}

Circle c(2.0);
printArea(c); // 调用 Circle::area
```

`printArea` 在编译期只知道参数是 `const Shape&`，具体调用 `Circle::area` 还是其他派生类的 `area`，是运行时通过对象的虚函数表（vtable）决定的。没有多态，`printArea` 要么只能处理一种具体类型，要么要在函数体里手写类型判断分支，新增一种形状就要去改这个函数，这正是"开闭原则"想避免的情况。多态让新增派生类型不需要改动已有的调用代码。

除了运行时多态（虚函数），C++ 还有编译期多态：函数重载和模板都属于这一类，调用哪个版本在编译期就确定下来，不依赖虚函数表，开销也更低。面试里说"C++ 的多态"默认指运行时多态，但能主动提一句编译期多态是加分项。

**常见追问 / 面试陷阱**

> 追问"多态是怎么实现的"，标准答案要落到虚函数表指针（vptr）和虚函数表（vtable）：每个含有虚函数的类有一张 vtable，存放该类各个虚函数的地址；每个该类对象里有一个隐藏的 vptr 指向本类的 vtable。通过基类指针调用虚函数时，先解引用 vptr 找到 vtable，再按函数在表中的槽位取地址调用，这一步是运行时完成的，因此叫"运行时多态"。常见陷阱是把"函数重载"也算成多态的一种然后混着讲，面试官通常想让你分清运行时多态（虚函数）和编译期多态（重载/模板）。

## 2. 访问权限：`public` / `protected` / `private` 与 `friend`

**核心结论**：类内部的访问权限（成员声明成 `public`/`protected`/`private`）和继承方式（`class D : public/protected/private B`）是两件独立的事，一个题目里经常需要把两者叠加起来判断最终的访问级别。基本规则是：继承方式给基类里 `public` 和 `protected` 成员的访问级别设一个"上限"，取原始访问级别和继承方式两者中更严格的一个；基类的 `private` 成员在派生类里永远不可直接访问，不管继承方式是什么。

单个成员的访问权限含义：

| 访问级别 | 类内部（成员函数） | 派生类 | 类外部 |
|---|---|---|---|
| `public` | 可访问 | 可访问 | 可访问 |
| `protected` | 可访问 | 可访问 | 不可访问 |
| `private` | 可访问 | 不可访问 | 不可访问 |

继承方式对基类成员在派生类中的访问级别的影响：

| 基类中的访问级别 | `public` 继承 | `protected` 继承 | `private` 继承 |
|---|---|---|---|
| `public` | `public` | `protected` | `private` |
| `protected` | `protected` | `protected` | `private` |
| `private` | 不可访问 | 不可访问 | 不可访问 |

注意"不可访问"不等于"不存在"：基类的 `private` 成员仍然作为子对象的一部分存在于派生类对象的内存布局里，只是派生类的代码不能直接读写它，只能通过基类自己提供的 `public`/`protected` 接口间接操作。

```cpp
class Base {
public:
    int a;
protected:
    int b;
private:
    int c;
};

class Derived : protected Base {
    // a 在 Derived 内部变成 protected，Derived 外部不能访问
    // b 在 Derived 内部仍是 protected
    // c 在 Derived 里完全不可访问（但内存里仍然占位）
};
```

`private` 继承和 `protected` 继承在实践中都远少于 `public` 继承。`public` 继承表达严格的 is-a 关系（`Derived` 对外表现得像一个 `Base`）；`private` 继承更接近"用 `Base` 实现 `Derived`"（has-a 的一种变体），既不希望暴露 `Base` 的接口，又需要访问其 `protected` 成员或者需要被基类的模板机制识别为其子类（比如 CRTP 场景）。默认继承方式不写时，`class` 是 `private`，`struct` 是 `public`，这一点会在第 7 节展开。

`friend` 是访问权限规则里唯一的"后门"：一个类可以显式声明某个函数或某个类为友元，被声明的函数/类可以访问这个类的 `private` 和 `protected` 成员，即使它本身既不是成员函数也不是派生类。

```cpp
class Matrix {
public:
    Matrix(double v) : val_(v) {}
    friend Matrix operator+(const Matrix& a, const Matrix& b); // 友元函数
    friend class MatrixDebugger; // 友元类

private:
    double val_;
};

Matrix operator+(const Matrix& a, const Matrix& b) {
    return Matrix(a.val_ + b.val_); // 直接访问私有成员 val_
}
```

`friend` 关系有两个容易考到的性质：不可传递（`A` 是 `B` 的友元，`B` 是 `C` 的友元，不代表 `A` 是 `C` 的友元），也不可继承（`Base` 声明的友元不会自动成为 `Derived` 的友元，反过来 `Derived` 声明的友元也不能访问只在 `Base` 里定义的私有成员，除非 `Base` 单独声明）。

**常见追问 / 面试陷阱**

> 追问"为什么要有 `friend`，这不是破坏封装吗"：`friend` 确实是有意打破封装边界的机制，典型场景是运算符重载（比如 `operator<<` 需要访问私有成员来打印，但它不能是成员函数，因为左操作数是 `ostream` 而不是这个类自己）、或者两个类紧密协作且不希望把接口暴露给其他任何人。面试官想听到的是"`friend` 是在封装原则下开的一个受控例外，声明权在类自己手里，被声明的一方不能反过来指定谁是自己的友元"，而不是简单说"用 `friend` 就能绕过权限检查"。

## 3. 六大默认成员函数：生成时机与隐式删除规则

**核心结论**：一个类最多有 6 个特殊成员函数：默认构造函数、析构函数、拷贝构造函数、拷贝赋值运算符，以及 C++11 起加入的移动构造函数、移动赋值运算符。编译器会在你不声明的前提下尝试隐式生成每一个，但"尝试生成"不等于"总能生成一个可用的版本"。当类的成员或基类的状态使得某个函数在语义上说不通时，编译器会把它隐式声明为 `= delete`，此时这个函数存在但不可调用，触发调用会在编译期报错，而不是在运行时。

先厘清一个高频混淆点：拷贝构造函数和拷贝赋值运算符的调用时机不同，靠"等号左边的对象是不是刚被创建出来"来判断。

```cpp
Widget a(1);
Widget b = a;   // 拷贝构造：b 是全新对象，用 a 初始化它
Widget c(2);
c = a;          // 拷贝赋值：c 已经存在（已经构造完毕），这里是给已有对象重新赋值
```

`Widget b = a;` 这种写法虽然用了 `=`，但因为 `b` 是在这条语句里第一次被定义，本质是初始化而不是赋值，调用的是拷贝构造函数；只有当赋值号左边的对象在此之前已经存在（已经完成过构造），才会调用拷贝赋值运算符。C++17 起对 `Widget b = a;` 这类拷贝初始化在满足条件时可以做到"拷贝消除"（copy elision），但语义上仍然把它归为拷贝构造场景，只是编译器被允许（C++17 起在纯右值场景是强制）跳过实际的构造函数调用。

**默认构造函数**：只要类没有用户声明任何构造函数（默认构造、拷贝构造、移动构造、带参数的构造函数中的任意一个），编译器就会隐式生成一个默认构造函数，对每个成员调用其默认构造函数、对内置类型成员不做初始化。一旦用户声明了任何一个构造函数（哪怕只是一个拷贝构造函数），默认构造函数就不会再被隐式生成，此时如果代码里还需要无参构造，必须自己写或者用 `= default` 显式要回来。

**析构函数**：没有用户声明时隐式生成，依次析构每个成员和基类子对象，顺序与构造相反。基类析构函数不是 `virtual` 时，通过基类指针 `delete` 派生类对象只会调用基类析构函数，派生类新增的资源不会被释放，这是"基类析构函数要不要声明为 `virtual`"这道经典题的根源。

**拷贝构造函数 / 拷贝赋值运算符隐式删除的触发条件**（对应 cppreference 的措辞，考试时说清楚这几条即可）：

| 触发条件 | 拷贝构造函数 | 拷贝赋值运算符 |
|---|---|---|
| 成员是引用类型（非右值引用） | 不删除：引用成员在拷贝构造时可以直接绑定到同一个被引用对象 | 删除：已绑定的引用不能重新指向别的对象，赋值语义无法实现 |
| 成员是右值引用类型 | 删除 | 删除 |
| 成员是 `const` 类型（非类类型） | 不删除：`const` 成员拷贝构造时可以直接用来初始化 | 删除：`const` 成员一旦初始化就不能再被赋值 |
| 成员/基类的对应函数被删除或不可访问（比如成员本身不可拷贝） | 删除 | 删除 |
| 类已声明了移动构造函数或移动赋值运算符（且未显式声明拷贝构造/拷贝赋值） | 删除 | 删除 |
| 基类把拷贝构造/拷贝赋值声明为 `private` 或 `= delete` | 删除 | 删除 |

表格里最容易考的两点：一是引用成员和 `const` 成员对拷贝构造和拷贝赋值的影响不对称（构造能过，赋值不能过）；二是"声明了移动语义就会连带删除拷贝语义"，这是 C++11 引入的一条规则，意图是提醒你：既然这个类的资源管理需要自定义移动逻辑（说明它管理着某种独占资源），那么编译器生成的逐成员拷贝很可能是错的，干脆不让它隐式存在，逼你要么显式写拷贝逻辑，要么承认这个类本来就不该被拷贝。

移动构造函数、移动赋值运算符的隐式生成条件比拷贝更苛刻：只有当类没有用户声明的拷贝构造函数、拷贝赋值运算符、移动赋值运算符（对移动赋值运算符则是没有用户声明的拷贝构造、拷贝赋值、移动构造）、也没有用户声明的析构函数时，编译器才会隐式生成移动构造/移动赋值。只要用户声明了析构函数、拷贝构造、或拷贝赋值中的任意一个，移动构造和移动赋值就完全不会被隐式声明。注意这里是"不声明"，不是"声明为删除"，效果是调用移动语义的地方会退化成调用拷贝构造/拷贝赋值（如果它们可用的话）。这也是为什么很多历史遗留类在 C++11 之后没有自动获得移动优化：只要它们写了自定义析构函数（哪怕只是打一行日志），移动构造就不会被自动生成。

关于拷贝构造/拷贝赋值和移动构造/移动赋值的详细代码对比放在下一节展开。

**常见追问 / 面试陷阱**

> 追问"这就是 Rule of Three / Rule of Five / Rule of Zero"：Rule of Three 指如果一个类需要自定义析构函数、拷贝构造函数、拷贝赋值运算符中的任意一个，通常三个都需要自定义（因为需要自定义析构大概率意味着类在管理某种资源，逐成员拷贝对这种资源大概率是错的）。C++11 之后扩展成 Rule of Five，把移动构造和移动赋值也算进来。Rule of Zero 则是更现代的建议：尽量不要在业务类里自己管理裸资源，把资源管理都下放给 `std::vector`、`std::unique_ptr`、`std::shared_ptr` 这类已经正确实现了 Rule of Five 的类型做成员，业务类自己一个特殊成员函数都不用写，编译器生成的版本天然正确。

## 4. 移动构造函数与拷贝构造函数对比

**核心结论**：拷贝构造函数从一个已存在对象复制出一份独立的新资源，原对象不受影响；移动构造函数从一个（通常是将亡的）右值对象那里把资源的所有权直接"偷"过来，不重新分配资源，代价是必须把原对象置于一个可安全析构的状态（通常是把指针置空、把大小置零）。移动构造函数应当标注 `noexcept`，否则在标准库容器扩容这类需要保证强异常安全的场景下，编译器会退化成使用拷贝构造，白白损失移动本该带来的性能收益。

用一个持有堆内存的简单类说明两者的区别：

```cpp
class Buffer {
public:
    explicit Buffer(size_t n) : size_(n), data_(new int[n]{}) {}

    // 拷贝构造：分配一块新内存，逐元素复制内容，两个对象此后互不影响
    Buffer(const Buffer& other)
        : size_(other.size_), data_(new int[other.size_]) {
        std::copy(other.data_, other.data_ + size_, data_);
    }

    // 移动构造：接管 other 的指针，不分配也不复制任何数据
    // 参数是右值引用 Buffer&&，表示 other 即将被销毁，可以放心拿走它的资源
    Buffer(Buffer&& other) noexcept
        : size_(other.size_), data_(other.data_) {
        other.size_ = 0;
        other.data_ = nullptr; // 必须置空：否则 other 析构时会 delete 已经转移走的内存
    }

    ~Buffer() { delete[] data_; }

private:
    size_t size_;
    int* data_;
};
```

移动构造函数的参数类型是右值引用（`Buffer&&`），只能绑定到右值（临时对象、`std::move` 显式转换后的左值）。函数体里做的事情本质是指针赋值，时间复杂度从拷贝构造的 $O(n)$ 降到 $O(1)$。关键的一步是把 `other.data_` 置成 `nullptr`：移动之后 `other` 依然会在它的作用域结束时被正常析构，如果不置空，`other` 的析构函数会对已经转移给新对象的内存再执行一次 `delete[]`，而新对象的析构函数稍后也会 `delete[]` 同一块内存，造成同一块内存被释放两次（double free），这是未定义行为。

**为什么移动构造函数应该标 `noexcept`**：`std::vector` 在扩容（容量不够，需要分配更大内存并把已有元素搬到新内存）时，必须保证强异常安全：如果搬迁过程中抛出异常，原 `vector` 必须保持完全不变。如果对每个元素直接调用移动构造，一旦移动到中途某个元素的移动构造函数抛出异常，此时旧内存里的部分元素已经被"掏空"（资源已经转移给新内存里的对象），旧 `vector` 已经不是原来的状态，无法安全回滚，强异常安全就被破坏了；而拷贝构造失败时旧对象完全没被动过，可以安全放弃新内存、保留旧数据。

因此标准库的做法是：扩容搬迁时统一调用 `std::move_if_noexcept`，它在元素类型的移动构造函数标了 `noexcept`（或者这个类型根本没有可用的拷贝构造函数，也就是只能移动的类型）时才真正转成右值触发移动，否则转成左值触发拷贝。也就是说，`Buffer` 的移动构造函数如果没有 `noexcept`，`vector<Buffer>` 在扩容时会退化成逐元素拷贝，性能上多了一遍完整的堆内存分配加复制，这种现象有个专门的名字叫 "vector pessimization"（vector 的移动悲观化）。

```cpp
// 简化后的 vector 扩容逻辑示意
for (size_t i = 0; i < old_size; ++i) {
    new (new_storage + i) T(std::move_if_noexcept(old_storage[i]));
}
```

| | 拷贝构造函数 | 移动构造函数 |
|---|---|---|
| 参数类型 | `const T&` | `T&&` |
| 资源处理方式 | 分配新资源并复制内容 | 直接接管原对象的资源 |
| 原对象状态 | 不受影响 | 被置空/置于可析构的有效状态 |
| 时间复杂度（持有堆内存场景） | $O(n)$ | $O(1)$ |
| 触发场景 | 用左值初始化新对象 | 用右值（临时对象、`std::move` 后的左值）初始化新对象 |
| 对 `vector` 扩容的影响 | 总是安全，但慢 | 只有标了 `noexcept` 才会被优先使用 |

**常见追问 / 面试陷阱**

> 追问"移动之后原对象处于什么状态，还能用吗"：标准只保证移动之后原对象处于"有效但未指定"（valid but unspecified）的状态，可以安全析构、可以安全赋新值，但不能假设它还保留原来的内容。自己写移动构造时，为了让这个约定更明确、更安全，通常直接把资源指针置空、把计数置零，而不是留一个不确定的中间状态。另一个常见陷阱是移动构造函数体内忘记 `noexcept`，代码功能上完全正确，但会在 `vector<Buffer>` 扩容这类场景里悄悄退化成拷贝，这种性能坑不会报错也不会有编译警告，只能靠了解这条规则来避免。

## 5. 深拷贝与浅拷贝

**核心结论**：浅拷贝只是把成员逐个复制一遍，如果成员是指针，复制的是指针本身（一个地址值），而不是指针指向的内容，结果是两个对象的指针成员指向同一块内存；深拷贝则会为新对象重新分配一块独立内存，并把原内存的内容复制过去，两个对象此后互不影响。编译器隐式生成的拷贝构造函数和拷贝赋值运算符默认做的是逐成员拷贝，也就是浅拷贝。如果成员里有裸指针，这就是一个隐患。

```cpp
class Naive {
public:
    explicit Naive(size_t n) : size_(n), data_(new int[n]{}) {}
    ~Naive() { delete[] data_; }
    // 没有自定义拷贝构造函数，编译器生成的版本只是把 data_ 这个指针值复制一遍

private:
    size_t size_;
    int* data_;
};

void trigger_double_free() {
    Naive a(10);
    Naive b = a;   // 隐式浅拷贝：b.data_ 和 a.data_ 是同一个地址
} // 作用域结束，a 和 b 依次析构，对同一块内存 delete[] 两次，未定义行为（double free）
```

两个对象的内存布局如下：

```text
a: [ size_ = 10 | data_ = 0x1000 ] ---\
                                        > 都指向同一块堆内存 [ int[10] ] at 0x1000
b: [ size_ = 10 | data_ = 0x1000 ] ---/
```

`a` 和 `b` 离开作用域时都会在析构函数里执行 `delete[] data_`，第二次 `delete[]` 操作的是一块已经被释放过的内存，行为未定义，实践中常见表现是程序崩溃或堆结构损坏导致后续毫不相关的内存分配出错。要修复这个问题，需要自己写深拷贝版本的拷贝构造函数和拷贝赋值运算符（参照第 4 节 `Buffer` 的拷贝构造函数写法），或者干脆用 `std::unique_ptr`/`std::vector` 替代裸指针，让资源管理交给已经正确实现拷贝控制的标准库类型（对应 Rule of Zero）。

需要区分：并非所有指针成员都要求深拷贝。如果指针指向的是这个类不拥有所有权的对象（比如一个观察者指针，指向外部管理的资源），浅拷贝反而是正确语义。深拷贝还是浅拷贝取决于这个类对指针指向的资源有没有所有权，而不是"看到指针就要深拷贝"。

**常见追问 / 面试陷阱**

> 追问"怎么判断一个类需不需要深拷贝"：看它的指针成员是不是这个类独占所有权的资源（这块内存的生命周期由这个类的构造/析构负责）。是独占所有权，就需要深拷贝或者禁止拷贝（把拷贝构造/拷贝赋值声明为 `= delete`，比如很多只能被移动的资源句柄类型）；只是持有一个指向外部对象的观察指针，浅拷贝没有问题，甚至深拷贝反而是错的（复制出一个新对象，但两者本该共享同一个外部资源）。

## 6. 空类的默认成员函数与 `sizeof` 大小

**核心结论**：一个没有写任何成员的空类，C++11 起编译器仍然会尝试隐式生成 6 个特殊成员函数（默认构造函数、析构函数、拷贝构造函数、拷贝赋值运算符、移动构造函数、移动赋值运算符），只要没有其他因素阻止它们生成（对空类来说没有任何阻止因素，所以 6 个全部会生成）。空类的 `sizeof` 结果是 1，而不是 0。

```cpp
class Empty {};

static_assert(sizeof(Empty) == 1, "空类大小恒为 1 字节（不考虑作为基类子对象的特殊情况）");
```

`sizeof` 不能是 0 的原因是数组和指针运算的一致性要求：如果 `sizeof(Empty) == 0`，那么 `Empty arr[2];` 里 `&arr[0]` 和 `&arr[1]` 会是同一个地址，破坏了"数组中每个元素地址不同"这条 C++ 对象模型的基本保证，也会让 `arr + 1` 这类指针运算失去意义。标准的做法是强制要求任何完整对象类型的大小至少为 1 字节，编译器通常会在空类里插入一个占位字节来满足这个要求。

这条"大小至少为 1"的规则只约束"最派生对象"（most-derived object），也就是不是作为其他类型子对象存在的、独立的完整对象。当一个空类作为另一个类的**基类**（不是作为成员）时，编译器被允许不为这个空基类子对象分配额外空间，这个优化叫**空基类优化**（Empty Base Optimization, EBO）：

```cpp
class Empty {};

class WithMember {
    Empty e_;   // 作为成员：sizeof(WithMember) 通常是 sizeof(int) 的整数倍再加上 e_ 至少占的 1 字节（可能有 padding）
    int x_;
};

class WithBase : private Empty {   // 作为基类：EBO 生效
    int x_;
};

// 典型情况下 sizeof(WithBase) == sizeof(int)，Empty 子对象不额外占用空间
// 但 sizeof(WithMember) 通常大于 sizeof(int)，因为 e_ 作为成员仍然要占至少 1 字节
```

EBO 之所以能对基类子对象生效，正是因为"大小非零"的规则只约束最派生对象，基类子对象不受这条规则约束，只要它不会和另一个同类型的子对象共享同一个地址（如果一个类同时把同一个空类当作两个不同的基类，或者空基类和第一个成员类型相同，EBO 会被禁用，避免这两个子对象地址重合）。这也是 `std::unique_ptr` 能在自定义 deleter 是空类（比如无状态的函数对象）时做到和裸指针一样大小的原因：它把 deleter 存成基类而不是普通成员。

**常见追问 / 面试陷阱**

> 追问"这 6 个函数具体做什么"：对空类而言，默认构造函数和析构函数都是空操作；拷贝构造函数、拷贝赋值运算符、移动构造函数、移动赋值运算符也都是空操作（因为没有成员可以拷贝或移动）。追问"C++98 时代空类有几个函数"：C++98/03 没有移动语义，只有 4 个（默认构造、析构、拷贝构造、拷贝赋值），移动构造和移动赋值是 C++11 才加入的特殊成员函数。

## 7. `struct` 与 `class` 的区别

**核心结论**：在 C++ 里，`struct` 和 `class` 唯一的语法差异是默认访问权限和默认继承方式：`struct` 的成员和继承默认是 `public`，`class` 默认是 `private`。除此之外二者能力完全相同：都可以有构造函数、析构函数、成员函数（含虚函数）、访问权限说明符、模板参数、继承其他类型。这一点经常和 C 语言的 `struct` 混淆：C 的 `struct` 只能包含数据成员，不能有成员函数、不能继承、没有访问控制概念，是纯粹的数据聚合体；C++ 的 `struct` 是 `class` 的一个"默认权限不同"的同义写法，在语言能力上没有阉割。

```cpp
struct S {
    int a;      // 默认 public
    void f() {} // struct 一样可以有成员函数
private:
    int b;      // struct 也可以显式用 private
};

class C {
    int a;      // 默认 private
public:
    void f() {}
};

struct D : S {};        // 默认 public 继承
class  E : public S {}; // 效果等价于上面
```

实践中的约定俗成是：`struct` 用来表示一组数据的简单聚合（POD 风格，通常没有不变量需要维护），`class` 用来表示带有行为和封装不变量的类型。这只是编码风格上的惯例，编译器不做任何区分。

**常见追问 / 面试陷阱**

> 追问"C++ 的 `struct` 是不是必须是 POD"：不是。C++ 的 `struct` 可以有构造函数、虚函数、私有成员，一旦这样写它就不再是 POD（Plain Old Data）类型，但仍然是合法的 `struct`。是否是 POD 由类型的具体定义决定（是否 trivial、是否 standard-layout），和用 `struct` 还是 `class` 关键字声明无关。

## 8. 结构体可以直接赋值吗

**核心结论**：可以，前提是结构体的每个成员都是可拷贝赋值的（编译器没有把拷贝赋值运算符隐式删除）。`a = b;` 这种写法调用的是编译器生成（或用户自定义）的拷贝赋值运算符，默认行为是逐成员赋值：内置类型成员直接赋值，数组成员逐元素赋值，类类型成员递归调用它自己的拷贝赋值运算符。

```cpp
struct Point { double x, y; };
struct Line  { Point a, b; };

Line l1{{0, 0}, {1, 1}};
Line l2;
l2 = l1; // 合法：Point 的成员都是 double，Line 的成员都是 Point，逐层可赋值
```

几种会让这个"直接赋值"变复杂或者失效的情况：

- **裸指针成员**：默认赋值只复制指针的地址值，不复制指针指向的内容，属于浅拷贝，可能带来和第 5 节相同的双重释放风险（如果这个结构体的析构逻辑会释放该指针）。
- **内置数组成员**：作为类的成员时，编译器生成的赋值运算符会对数组做逐元素赋值（`int arr[5];` 这个成员会被逐个 `int` 赋值）；但要注意这只在它是某个类/结构体的成员时成立，两个独立的裸数组变量之间不能直接用 `=` 赋值（`int a[5], b[5]; a = b;` 是编译错误，因为数组类型不可赋值，数组名会退化成指针参与运算而不是整体赋值）。
- **引用类型成员、`const` 类型成员**：这两种成员一旦初始化后不能重新绑定或重新赋值，会导致整个结构体的拷贝赋值运算符被隐式删除，此时 `l2 = l1;` 这类语句在编译期报错。
- **成员本身不可赋值**（比如成员类型自己把拷贝赋值运算符删除了，例如成员是 `std::unique_ptr`）：同样导致外层结构体的拷贝赋值运算符被隐式删除。

```cpp
struct Broken {
    int& ref;         // 引用成员
    const int c;      // const 成员
};

Broken b1{...}, b2{...};
// b1 = b2; // 编译错误：Broken 的拷贝赋值运算符被隐式删除
```

**常见追问 / 面试陷阱**

> 追问"结构体赋值和 `memcpy` 有什么区别"：对于trivially copyable（平凡可拷贝）的结构体，编译器生成的赋值运算符在效果上等价于按字节拷贝，和 `memcpy` 效果相同，编译器也确实经常把这种赋值优化成底层的按字节拷贝。但一旦结构体里有非平凡的成员（比如内部有自定义拷贝赋值逻辑的类类型成员、虚函数表指针），赋值运算符会调用每个成员各自的拷贝赋值运算符而不是简单地按字节复制，这时候用 `memcpy` 替代赋值是不安全的，会跳过必要的资源管理逻辑。

A. C++11 起，编译器会为其隐式生成默认构造、析构、拷贝构造、拷贝赋值、移动构造、移动赋值共 6 个特殊成员函数
B. `sizeof(Empty)` 的结果恒为 0，因为它没有任何数据成员
C. `sizeof(Empty)` 的结果是 1，目的是保证 `Empty` 类型数组中每个元素的地址不同
D. 当 `Empty` 作为另一个类的基类而不是成员时，可能通过空基类优化（EBO）不占用额外空间

title: 快速选择题 12
question: 下列关于"Rule of Five"的说法，正确的是：
answer: B
A. 一个类只要写了自定义析构函数，就一定要同时手写全部五个特殊成员函数，否则代码无法通过编译

C. Rule of Five 是编译器强制检查的规则，违反会导致编译错误
D. 只要遵守 Rule of Five，就不需要考虑 Rule of Zero
explanation: Rule of Five 是工程实践上的经验法则而不是编译器强制规则（A、C 错误）；更现代的建议是尽量遵循 Rule of Zero，把资源管理下放给 `std::unique_ptr`/`std::vector` 等已经正确实现 Rule of Five 的类型，业务类本身不手写这五个函数，二者是互补而不是互斥的关系（D 错误）。
