# 性能优化 2 · 多线程与 CPU 优化

量化交易系统（尤其是撮合引擎、行情处理、做市报价这类低延迟路径）对多线程性能的要求和普通后端服务不在一个量级：普通服务关心"吞吐够不够"，量化系统往往还要关心"延迟的尾部有多长、抖动有多大"，而多线程环境下最隐蔽的延迟杀手往往不是算法复杂度，而是 cache 一致性开销、锁竞争、跨 NUMA 节点访存这些贴着硬件层面的问题。这一讲从 cache 层级出发，讲清楚 false sharing 为什么会在两个线程逻辑上互不相关的情况下依然互相拖慢，再展开锁竞争优化、线程池调参、CPU 亲和性与 NUMA、以及操作系统调度器的基础知识。这些话题在面试里经常以"你的程序在多核上跑反而比单核慢，可能是什么原因"这类开放题出现，回答的关键是能把"现象"和"底层机制"对应起来，而不是罗列关键词。

```text
1. 遇到"多线程性能不升反降"类问题，先按这个顺序排查：是不是锁竞争太重（临界区太大/锁粒度太粗）、是不是 false sharing（几个线程各自写的变量挤在同一条 cache line）、是不是线程数超过了硬件并行能力导致频繁上下文切换、是不是跨 NUMA 节点访存拖慢了内存密集型任务。
2. 遇到 cache 相关的题，先在脑子里画出层级图：L1(~4 cycles) < L2(~12 cycles) < L3(~40 cycles) < 主存(~200+ cycles)，cache 以 64 字节的 cache line 为最小搬运单位，这两点是解释 false sharing、数据局部性问题的共同前提。
3. 遇到"两个线程各写各的变量却互相变慢"这类描述，第一反应是 false sharing：检查这两个变量是不是被分配到了同一条 cache line，而不是去查两个线程之间有没有真正的数据竞争(data race)。
4. 遇到锁优化题，先问"临界区里哪些操作是必须互斥的，哪些是可以挪到锁外的"，再问"读写比例是不是悬殊到值得换读写锁"，再问"这把锁保护的数据能不能按 key 分片成多把锁"，无锁结构留到前面几种手段都不够用时再考虑。
5. 遇到线程池大小、CPU 绑核、NUMA 相关的题，先分清任务是 CPU 密集型还是 IO 密集型，这个判断直接决定了后续所有参数（线程数量级、要不要绑核、要不要关心内存分配的 NUMA 节点）该往哪个方向调。
```

## 1. CPU cache 层级与 cache line 复习

**核心结论**：现代 CPU 的存储层级从寄存器往下依次是 L1、L2、L3 cache，再往下是主存（DRAM），层级越靠近核心，容量越小、延迟越低；层级之间以固定大小的**cache line**（现代 x86-64 和 ARM 平台通常是 **64 字节**）为最小搬运单位，CPU 读写内存时哪怕只访问 1 个字节，也会把这个字节所在的整条 cache line 一次性搬进更靠近核心的层级。这条"以 cache line 为最小单位搬运"的规则是理解本讲后面 false sharing 问题的全部前提。

典型延迟量级（以主流 x86-64 桌面/服务器 CPU 为例，具体数值随微架构、频率、是否命中 TLB 等因素浮动，面试里给数量级即可，不需要死记精确周期数）：

| 层级 | 典型容量 | 典型延迟（周期数） | 典型延迟（时间，3GHz 参考） |
|---|---|---|---|
| L1 cache（每核心独占） | 32~48 KB | ~4~5 cycles | ~1~2 ns |
| L2 cache（每核心独占或少数核心共享） | 256KB~1MB | ~10~14 cycles | ~4~5 ns |
| L3 cache（全核心共享） | 数 MB~数十 MB | ~40~60 cycles | ~15~20 ns |
| 主存（DRAM） | GB 级 | ~200~300+ cycles | ~70~100+ ns |

每往下一层，延迟大约是上一层的一个数量级，这就是为什么"数据是不是在 cache 里"往往比算法的大 O 复杂度更直接地决定实际运行时间：一段时间复杂度更差但访存局部性更好的代码，实际跑起来经常反而更快。

```text
CPU0                                CPU1
┌────────┐                          ┌────────┐
│  L1     │ ~1-2ns                  │  L1     │
├────────┤                          ├────────┤
│  L2     │ ~4-5ns                  │  L2     │
└───┬────┘                          └───┬────┘
    │            ┌───────────┐          │
    └───────────▶│    L3      │◀────────┘
                 │  (共享)     │ ~15-20ns
                 └─────┬──────┘
                       │
                 ┌─────▼──────┐
                 │  主存 DRAM  │ ~70-100ns+
                 └────────────┘
```

**cache line 是一致性协议的最小粒度**：多核 CPU 之间维护 cache 一致性（各核心看到的同一块内存内容始终一致）靠的是类似 MESI 的协议，而这类协议的操作单位是整条 cache line，不是单个字节或单个变量。也就是说，硬件层面根本没有"只让这条 cache line 里的某一个变量失效"这种能力，只要 cache line 里任何一个字节被别的核心写过，整条 line 在本地核心的副本都会被判定失效。这个粒度上的"锁定"正是第 2 节 false sharing 问题的根源。

**常见追问 / 面试陷阱**

> 追问"为什么 cache line 选 64 字节，不是更大或更小"：这是一个在命中率和总线带宽之间的工程权衡。cache line 越大，一次预取搬运的连续数据越多，对顺序访问模式（比如遍历数组）更友好，命中率通常更高；但 line 越大，一次总线传输占用的带宽和延迟也越高，如果程序访存模式比较随机，大 line 里大部分数据其实用不上，等于浪费带宽，还会加剧 false sharing 的概率（同一条 line 里能塞下更多互不相关的变量）。64 字节是过去二十年间 x86 和 ARM 主流实现共同收敛到的一个经验最优点，不是理论上唯一正确的数字。

## 2. False sharing（伪共享）详解

**核心结论**：false sharing 指的是多个线程各自频繁读写**逻辑上完全独立、互不依赖**的变量，但这些变量恰好被编译器或内存分配器放进了同一条 cache line，导致 cache 一致性协议把它们当成"同一份共享数据"来处理，每次某个核心写自己的变量，都会让持有这条 line 副本的其他核心的 cache 失效，逼迫对方下次访问时重新从更慢的层级拉取数据。即使两个线程从数据依赖的角度看根本不存在竞争(race)，性能依然会被互相拖累。

**具体例子**：假设一个 `struct` 里有两个字段 `a` 和 `b`，线程 1 只写 `a`，线程 2 只写 `b`，两者之间没有任何逻辑关联：

```cpp
struct Counters {
    int a; // 线程 1 独占写
    int b; // 线程 2 独占写
};

Counters counters;

// 线程 1
void thread1() {
    for (int i = 0; i < 100000000; ++i) {
        counters.a++;
    }
}

// 线程 2
void thread2() {
    for (int i = 0; i < 100000000; ++i) {
        counters.b++;
    }
}
```

`int a` 和 `int b` 加起来只占 8 字节，远小于 64 字节的 cache line，编译器默认会把它们紧挨着分配在同一条 cache line 上。表面上两个线程各写各的，没有数据竞争，逻辑完全正确，但实测这段代码的吞吐会远低于把 `a`、`b` 分别放在两条独立 cache line 上的版本，差距在典型多核平台上可以达到数倍。

**MESI 协议下发生了什么**：MESI 给每条 cache line 标记 Modified / Exclusive / Shared / Invalid 四种状态之一。当线程 1 所在的核心（CPU0）要写 `a` 时，它必须先把这条 cache line 提升到 Modified（或先经过 Exclusive）状态，这个过程会通过总线/互联广播一条失效消息，把其他核心（CPU1）里持有同一条 line 副本的状态置为 Invalid。此时如果 CPU1 正准备写 `b`（同一条 line 上的另一个字段），它会发现本地副本已失效，必须重新从 CPU0 或者更下层的 L3/主存把整条 line 拉回来，再提升到 Modified 状态。这个动作反过来又会让 CPU0 的副本失效。两个线程各自的写操作交替进行时，这条 cache line 就在两个核心之间来回"乒乓"，每一次乒乓都要付出一次跨核心的 cache 一致性流量和几十到上百周期的延迟，而这一切只是因为 `a` 和 `b` physically 挤在了同一条 line 上，和它们逻辑上有没有关联毫无关系。

```text
              同一条 64 字节 cache line
        ┌───────────────────────────────┐
        │  int a (offset 0)   int b (offset 4)  │
        └───────────────────────────────┘
CPU0 写 a               CPU1 写 b
  │                        │
  ▼                        ▼
line 提升为 M(CPU0)   →  广播失效  →  CPU1 副本变 Invalid
                                          │
                          CPU1 写 b 需要重新拉取整条 line
                                          ▼
line 提升为 M(CPU1)   →  广播失效  →  CPU0 副本变 Invalid
  │
  ▼
CPU0 再次写 a 又需要重新拉取整条 line ……（循环乒乓）
```

**解决方案一：用 `alignas` 把变量分别对齐/填充到独立的 cache line**。C++17 标准库提供了 `std::hardware_destructive_interference_size`（`<new>` 头文件），表示"两个对象之间需要间隔多少字节才能避免落入同一条 cache line"，通常等于目标平台的 L1 cache line 大小（多数 x86-64 平台上是 64）：

```cpp
#include <new>

struct alignas(std::hardware_destructive_interference_size) PaddedCounters {
    alignas(std::hardware_destructive_interference_size) int a; // 独占一条 cache line
    alignas(std::hardware_destructive_interference_size) int b; // 独占另一条 cache line
};
```

对比没有 padding 的版本：

```cpp
// 有 false sharing 风险：a、b 大概率落在同一条 cache line
struct Counters {
    int a;
    int b;
};

// 消除 false sharing：a、b 分别对齐到独立 cache line 边界，代价是结构体从 8 字节膨胀到 128 字节
struct PaddedCounters {
    alignas(64) int a;
    alignas(64) int b;
};
```

代价很直接：为了拆开两个只占 4 字节的 `int`，结构体体积膨胀到 128 字节（两条 cache line），这是用空间换并发性能的典型取舍，只应该用在**确定会被多线程高频并发写**的字段上，不应该无差别地给所有结构体加 padding，否则会增加内存占用、降低 cache 利用率、甚至在数据被顺序遍历的场景里因为占用更多 cache line 反而拖慢访问。

**解决方案二：thread-local 变量**。如果每个线程只关心自己的一份计数器，不需要和其他线程共享同一个对象，最彻底的做法是用 `thread_local` 让每个线程拥有独立的存储，从根源上消除"多个线程写同一片内存"这个前提，自然不存在 false sharing：

```cpp
thread_local long local_counter = 0;

void worker() {
    for (int i = 0; i < 100000000; ++i) {
        local_counter++; // 每个线程操作自己独立的存储，互不干扰
    }
}
// 需要汇总时再显式收集每个线程的 local_counter
```

**常见追问 / 面试陷阱**

> 追问"false sharing 会不会导致结果错误"：不会。false sharing 纯粹是性能问题，不是正确性问题：每个线程读写的仍然是自己该读写的变量，数据本身不会错乱，只是因为 cache 一致性协议的失效/重新拉取开销，实际吞吐远低于预期。这一点经常和"数据竞争(data race)"混淆：data race 是多个线程无同步地读写同一个内存地址导致结果未定义，false sharing 是多个线程读写不同地址但共享同一条 cache line 导致性能下降，两者本质不同，但现象都表现为"多线程比预期慢"，容易在描述题里被出题人故意混着问。

> 追问"怎么定位 false sharing"：常见工具是 `perf c2c`（Linux perf 的 cache-to-cache 分析模式），它能直接列出哪些内存地址在不同核心间发生了频繁的 cache line 迁移和 HITM（hit-modified）事件，这是定位 false sharing 最直接的手段，比靠猜测和人工审查结构体布局效率高得多。

## 3. 锁竞争优化

**核心结论**：锁竞争的本质是"多个线程排队等待同一把互斥资源"，优化思路不外乎三个方向：缩短每次持锁的时间、降低线程真正需要互斥的概率、或者彻底避免阻塞式等待。三种手段的实现复杂度依次递增，面试和实际工程里都应该按这个顺序优先尝试。

**减小临界区范围**：只把真正需要互斥保护的操作放进锁的作用域，能在锁外完成的计算（尤其是耗时的部分，比如序列化、格式化、非共享数据的准备工作）尽量搬到锁外执行，缩短其他线程等待这把锁的时间：

```cpp
// 临界区过大：耗时的格式化操作也被锁保护，其他线程被迫多等
void bad_update(SharedState& state, const Data& data) {
    std::lock_guard<std::mutex> lock(state.mtx);
    std::string formatted = expensive_format(data); // 和共享状态无关，不该在锁内做
    state.value += formatted.size();
}

// 缩小临界区：耗时操作挪到锁外，锁内只保留真正需要互斥的一行
void good_update(SharedState& state, const Data& data) {
    std::string formatted = expensive_format(data); // 锁外完成
    {
        std::lock_guard<std::mutex> lock(state.mtx);
        state.value += formatted.size(); // 只有这一步需要互斥
    }
}
```

**读写锁替代普通互斥锁**：如果访问模式是读多写少（比如一份配置表大部分时间被高频查询，偶尔才更新），普通 `std::mutex` 会让所有读操作互相排队，即使读操作之间本来毫无冲突；换成读写锁（`std::shared_mutex`，C++17 起标准库支持）后，多个读者可以同时持有共享锁并发读取，只有写者需要独占锁，大幅降低读多写少场景下的等待时间：

```cpp
#include <shared_mutex>

class ConfigStore {
    mutable std::shared_mutex mtx_;
    std::unordered_map<std::string, std::string> data_;
public:
    std::string get(const std::string& key) const {
        std::shared_lock lock(mtx_); // 共享锁，多个读者可并发持有
        return data_.at(key);
    }
    void set(const std::string& key, std::string value) {
        std::unique_lock lock(mtx_); // 独占锁，写者之间、读写者之间互斥
        data_[key] = std::move(value);
    }
};
```

**分片锁（lock striping / sharding）**：如果一个大的共享数据结构（典型如哈希表）本来只用一把全局锁保护，所有线程无论操作的是不是同一个 bucket 都要互相排队；把这一把大锁拆成 N 把细粒度锁，每把锁只保护数据结构里的一部分（比如按 bucket 取模分配），可以让操作不同分片的线程完全并行，只有恰好落在同一个分片上的操作才需要互斥：

```cpp
template <typename K, typename V, size_t NumShards = 16>
class ShardedHashMap {
    struct Shard {
        std::mutex mtx;
        std::unordered_map<K, V> map;
    };
    std::array<Shard, NumShards> shards_;

    Shard& shard_for(const K& key) {
        size_t idx = std::hash<K>{}(key) % NumShards;
        return shards_[idx];
    }
public:
    void set(const K& key, V value) {
        Shard& s = shard_for(key);
        std::lock_guard<std::mutex> lock(s.mtx); // 只锁这一个分片，不影响其他分片的并发操作
        s.map[key] = std::move(value);
    }
    bool get(const K& key, V& out) {
        Shard& s = shard_for(key);
        std::lock_guard<std::mutex> lock(s.mtx);
        auto it = s.map.find(key);
        if (it == s.map.end()) return false;
        out = it->second;
        return true;
    }
};
```

分片数量的选择要权衡：分片越多，理论上并发度越高，但也意味着更多把锁对象占用内存，以及一些需要跨分片的操作（比如遍历整个 map、统计总大小）实现起来更复杂，通常取和线程数量同数量级或略多的一个 2 的幂。

**无锁（lock-free）数据结构**：基于原子操作（`std::atomic`）和 **CAS（compare-and-swap）** 实现，线程不需要阻塞等待锁被释放、也不会触发操作系统层面的上下文切换，理论上能提供更好的吞吐和更低的延迟抖动。但代价是实现复杂度显著上升：需要仔细处理内存序（memory order）、避免 **ABA 问题**（一个值从 A 变成 B 又变回 A，CAS 检测不到中间发生过变化，可能导致逻辑错误，常见解法是带版本号的 CAS 或者危险指针 hazard pointer），一旦设计有误，产生的 bug 往往难以复现和调试。工程实践里的优先级是：先尝试缩小临界区、读写锁分离、分片锁这几种代价更低、正确性更容易保证的手段，只有在这些手段都无法满足延迟要求、且团队有能力驾驭无锁结构的复杂度时，才考虑自己实现或引入无锁数据结构。

| 手段 | 适用场景 | 实现复杂度 | 主要收益 |
|---|---|---|---|
| 缩小临界区 | 几乎所有场景的第一步优化 | 低 | 减少其他线程等待时间 |
| 读写锁 | 读多写少 | 低 | 读操作可并发 |
| 分片锁 | 数据可按 key 自然拆分（哈希表、订单簿） | 中 | 不同分片完全并行 |
| 无锁结构（CAS） | 延迟极敏感、且团队能驾驭复杂度 | 高 | 避免阻塞和上下文切换，但要处理 ABA 等问题 |

**常见追问 / 面试陷阱**

> 追问"分片锁能不能完全消除锁竞争"：不能，只是把竞争的粒度从"整个数据结构"降低到"落在同一分片的操作之间"。如果 key 的哈希分布不均匀，导致大量操作集中落在少数几个分片上，分片锁的效果会明显打折扣，这是分片锁失效的典型场景，面试里经常作为追问出现。

## 4. 线程池大小的确定

**核心结论**：线程池大小没有一个通用的"正确数字"，关键在于先判断任务是 **CPU 密集型** 还是 **IO 密集型**，两类任务对线程数的最优取值方向完全相反。

**CPU 密集型任务**（比如数值计算、序列化、压缩）：线程在执行期间几乎一直占用 CPU，不会主动让出。这类任务的线程数应该接近物理核心数（或者逻辑核心数，取决于是否开启超线程），线程数一旦超过硬件能同时并行执行的数量，多出来的线程并不会带来更多有效计算能力，反而会因为操作系统频繁在线程间做上下文切换（保存/恢复寄存器状态、刷新部分 cache/TLB 内容）而增加开销，实际吞吐可能不升反降。

**IO 密集型任务**（比如网络请求、磁盘读写、等待外部服务响应）：线程执行期间大部分时间处于阻塞等待状态，不占用 CPU。这类任务的线程数可以远超核心数，因为某一时刻真正在 CPU 上运行的线程数量远小于线程池总数，其余线程都在等待 IO 完成，增加线程数主要是为了让更多请求能够同时"在途"，提高整体吞吐，而不是提高单个 CPU 核心的利用率。

**估算公式**：

$$
N_{\text{threads}} = N_{\text{cores}} \times \left( 1 + \frac{\text{等待时间}}{\text{计算时间}} \right)
$$

其中 $N_{\text{cores}}$ 是可用的 CPU 核心数；等待时间(wait time)是任务里线程处于阻塞状态（等待 IO、等待锁、等待其他线程）的时间；计算时间(compute time)是任务里线程真正占用 CPU 执行指令的时间。这个公式的直觉是：如果一个任务的生命周期里大部分时间在等待而不在计算，那么单个核心在等待期间是"空闲"的，可以安排更多线程来填满这段空闲时间；等待时间和计算时间的比值越大，需要的线程数就越多。对纯 CPU 密集型任务，等待时间趋近于 0，公式退化为 $N_{\text{threads}} \approx N_{\text{cores}}$；对等待时间是计算时间 9 倍的高度 IO 密集型任务，公式给出 $N_{\text{threads}} \approx 10 \times N_{\text{cores}}$。

这个公式只是一个**起点**，不是最终答案。等待时间和计算时间的比例通常来自经验估计或者初步压测，实际系统里还受内存带宽、下游服务并发容量、锁竞争引入的额外等待等因素影响，最终的线程池大小应该通过压测（观察吞吐、延迟分布随线程数变化的曲线，找到拐点）来确定和调整，而不是套公式算出一个数字就直接上生产。

**常见追问 / 面试陷阱**

> 追问"线程池设太大有什么具体坏处，不是线程多总能榨干更多并发吗"：坏处不只是上下文切换开销。线程数过多还会增加内存占用（每个线程有自己的栈，默认通常几 MB）、增加锁竞争的线程数量（本来 4 个线程抢一把锁和 400 个线程抢一把锁，等待队列长度完全不是一个量级）、以及在 CPU 密集型场景下让调度器需要更频繁地做调度决策，这些开销都会抵消"看起来并发度更高"带来的收益，所以线程池大小不是越大越好，而是要匹配任务类型和硬件并行能力。

## 5. CPU 亲和性（affinity）与 NUMA

**核心结论**：CPU 亲和性(affinity)是指把一个线程绑定到指定的一个或一组 CPU 核心上运行，操作系统调度该线程时只会在这些核心里选择，不会迁移到其他核心；NUMA(Non-Uniform Memory Access，非一致内存访问) 是多路服务器的一种内存架构，每个 CPU socket 拥有自己直连的本地内存，访问本地内存的延迟明显低于访问挂在另一个 socket 上的"远端"内存。这两个话题经常一起出现，因为绑核策略如果不考虑 NUMA 拓扑，很容易把线程绑在一个 socket 的核心上，却让它频繁访问另一个 socket 的内存，得不偿失。

**CPU 亲和性 API**：Linux 上常用 `sched_setaffinity`（进程级）和 `pthread_setaffinity_np`（线程级，`np` 表示 non-portable，是 glibc 的扩展而非 POSIX 标准的一部分）把线程绑定到指定核心集合：

```cpp
#include <pthread.h>
#include <sched.h>

void bind_current_thread_to_core(int core_id) {
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(core_id, &cpuset);
    pthread_setaffinity_np(pthread_self(), sizeof(cpu_set_t), &cpuset);
}
```

**绑核的好处**：减少线程在核心之间迁移带来的开销。线程一旦被调度到新核心，原来核心上积累的 L1/L2 cache 内容和 TLB（页表缓存）条目对新核心毫无用处，需要重新预热，绑核可以避免这种反复的"冷启动"，对延迟敏感的低延迟交易路径（比如行情处理线程、订单发送线程）尤其重要，工程上常见做法是把这类关键线程绑定到专用核心，甚至把这些核心从操作系统的常规调度中隔离出来（`isolcpus` 内核参数），只留给指定进程使用。

**绑核的坏处**：可能造成负载不均衡。如果手工分配的核心和实际负载不匹配（比如把多个高负载线程绑到了同一个核心），操作系统调度器原本可以自动把线程迁移到空闲核心来平衡负载，绑核之后这条自动平衡的路径被人为关闭，负载不均衡的问题必须由开发者自己规划解决，而不是依赖调度器兜底。

**NUMA 架构**：多路（multi-socket）服务器里，每个物理 CPU（socket）都直连一部分内存条，这部分内存对该 socket 上的核心来说是"本地内存(local memory)"，访问延迟低；访问挂在另一个 socket 上的内存则需要经过 socket 间的互联通道（如 Intel 的 UPI、AMD 的 Infinity Fabric），是"远端内存(remote memory)"，延迟明显更高，通常是本地访问的 1.5~2 倍甚至更多。

```text
        Socket 0                              Socket 1
   ┌─────────────────┐   互联(UPI/Infinity   ┌─────────────────┐
   │  Core0 Core1 ... │   Fabric)             │  Core0 Core1 ... │
   │   L1/L2 每核独占  │◀────────────────────▶│   L1/L2 每核独占  │
   │   L3 (共享)       │     跨 socket访问       │   L3 (共享)       │
   └────────┬─────────┘     延迟更高            └────────┬─────────┘
            │ 本地访问，延迟低                            │ 本地访问，延迟低
            ▼                                            ▼
   ┌─────────────────┐                          ┌─────────────────┐
   │  本地内存 DRAM 0  │                          │  本地内存 DRAM 1  │
   └─────────────────┘                          └─────────────────┘
```

**NUMA-aware 编程**的基本思路是尽量让一个线程访问的数据分配在它所在 socket 的本地内存里，避免频繁跨 socket 访存。常见手段包括：用 `numactl` 命令行工具启动进程时指定它绑定的 CPU 节点和内存节点（比如 `numactl --cpunodebind=0 --membind=0 ./my_program`）；在代码里通过 `libnuma` 库显式查询 NUMA 拓扑、在指定节点上分配内存；依赖 **first-touch 分配策略**：多数操作系统默认在虚拟内存页第一次被实际写入（而不是仅仅被 `malloc` 分配）时才真正绑定物理内存页，绑定的物理页会优先落在触发这次写入的线程所在的 NUMA 节点上，所以让"负责初始化某块内存的线程"和"之后主要使用这块内存的线程"保持在同一个 socket 上，可以借助 first-touch 策略自然获得较好的本地性，不需要每次都手动指定节点。

**常见追问 / 面试陷阱**

> 追问"是不是所有多线程程序都应该做 NUMA 优化"：不是。NUMA 优化主要针对内存带宽敏感或延迟极度敏感、且部署在真正的多路服务器上的场景；单路服务器（只有一个 socket）不存在远端内存的问题，NUMA 调优没有意义；即使在多路服务器上，如果程序的内存访问量很小或者对延迟不敏感，引入 `numactl`/`libnuma` 带来的工程复杂度也未必划算，应该先用 `numastat`、`perf` 等工具确认确实存在明显的跨节点访存开销，再决定要不要投入做 NUMA-aware 优化。

## 6. 操作系统调度器基础

**核心结论**：Linux 默认的进程/线程调度器是 **CFS（Completely Fair Scheduler，完全公平调度器）**，核心思想是让每一个可运行的任务获得的 CPU 时间尽量按权重成比例地"公平"，而不是像更早的调度器那样依赖固定长度的时间片轮转。理解 CFS 的基本机制，有助于理解为什么应用层的性能优化（线程池设计、绑核策略）终究要在调度器允许的框架内进行，而不能完全脱离调度器的行为假设。

**vruntime 机制**：CFS 给每个可运行任务维护一个**虚拟运行时间(vruntime)**，任务实际占用 CPU 执行的时间会累加到它的 vruntime 上（进行了按权重的换算，权重来自任务的 nice 值），CFS 调度器所有可运行任务按 vruntime 排序维护在一棵**红黑树**里，每次需要选择下一个运行的任务时，直接取树中 vruntime 最小（红黑树最左侧）的那个任务来运行。一个任务运行得越多，它的 vruntime 增长得越快，就会被排到树的更右侧，让位给其他 vruntime 更小、也就是"欠 CPU 时间更多"的任务，从而在长期运行下让所有同权重任务获得的 CPU 时间趋于相等。这就是"完全公平"名字的由来。红黑树的 $O(\log n)$ 插入、删除、查找最小值的时间复杂度，使得调度器在任务数量较多时依然能高效地做出调度决策。

```text
红黑树按 vruntime 排序（示意，最左节点 vruntime 最小，是下一个被调度的任务）：

                    vruntime=120
                   /            \
          vruntime=80          vruntime=200
         /          \
  vruntime=50    vruntime=100
  ▲
  下一个被调度的任务（vruntime 最小，欠 CPU 时间最多）
```

**用户可以影响、但不能完全控制调度决策**：应用层能通过 **nice 值**（`nice`/`renice` 命令，或 `setpriority` 系统调用，范围通常是 -20 到 19，数值越低优先级越高）调整任务的权重，权重越高的任务 vruntime 增长得越慢，会更频繁地被调度到；也能通过前一节的 CPU 亲和性 API 限制任务只能在指定核心上被调度。但这些手段都只是在给调度器"施加倾向性的约束和提示"，最终具体在哪个时刻、运行多长时间、是否被抢占，仍然由内核调度器根据当前所有可运行任务的整体状态动态决定，应用层无法精确控制到"这个线程必须在这一纳秒运行"的程度（除非切换到实时调度策略如 `SCHED_FIFO`/`SCHED_RR`，那是另一套完全不同的调度语义，脱离了 CFS 的"公平"目标，属于更专门的实时系统话题）。这正是为什么线程池设计、绑核这些应用层优化手段，本质上都是在"调度器允许的框架内"引导系统朝更优的方向运行，而不是取代调度器。理解这一点，才能对"为什么绑核之后性能还是不如预期"这类问题给出准确的解释：多半是因为其他因素（负载不均衡、共享资源竞争）抵消了绑核本身的收益，而不是绑核操作本身失效了。

**常见追问 / 面试陷阱**

> 追问"nice 值调到最高（-20）能不能保证这个线程永远优先运行"：不能。nice 值只是调整任务的权重，影响它的 vruntime 增长速度和在红黑树中被选中的相对频率，权重再高也只是"更频繁地被优先调度"，不是独占 CPU 或者阻止其他任务运行；真正需要"这个任务几乎必须立刻抢占其他任务运行"这种语义时，需要用实时调度策略（`SCHED_FIFO`/`SCHED_RR`）而不是调整 CFS 下的 nice 值，两者是完全不同的调度类别，不能用调整参数的方式从 CFS 语义过渡到实时语义。

```quiz
B. 每个 socket 有自己直连的本地内存，访问本地内存比访问其他 socket 的远端内存延迟更低
C. NUMA 架构只存在于单路（单 socket）服务器上
D. `numactl`、`libnuma` 这类工具/库的作用是关闭 NUMA 特性，让所有内存访问延迟一致
explanation: NUMA 架构下每个 socket 拥有直连的本地内存，访问本地内存的延迟明显低于经由 socket 间互联访问远端内存的延迟，这正是"非一致内存访问"名字的含义；A、C 说法错误，D 错误，这些工具的作用是帮助程序感知并利用 NUMA 拓扑（把线程和它常用的内存绑定在同一节点），而不是关闭 NUMA 特性。
```
