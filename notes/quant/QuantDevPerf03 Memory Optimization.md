# 性能优化 3 · 内存性能优化

前面的 C++ 系列已经讲清楚了内存分区、`struct` 对齐、`new`/`delete` 与 `malloc`/`free` 的语义差异，这些是"内存里有什么、怎么分配"的基础知识。这一讲往前一步，讨论"内存操作本身的性能"：为什么高频分配/释放会拖慢程序、高性能分配器靠什么机制绕开这些开销、数据结构的内存排布如何影响缓存命中率，以及虚拟内存翻译这条几乎不会被应用层代码直接看到的路径如何反过来限制性能。量化开发场景里，行情处理、订单簿维护、回测引擎这类高吞吐路径对内存性能极其敏感，这一讲的内容基本都是面试里"如何优化一段热路径代码"追问链的标准落点。

```text
1. 遇到"分配器在高并发下变慢"类问题，先定位是哪一类开销：全局锁竞争、内存碎片，还是频繁触发系统调用；三者的解法不同，不要笼统地回答"换个分配器"。
2. 遇到 tcmalloc/jemalloc 原理题，抓住两个核心机制：线程本地缓存（绕开锁）、按大小分级（减少碎片、O(1) 复用），大对象走独立路径是补充点，不是核心。
3. 遇到"自己实现一个内存池"类题目，先想清楚它管理的是不是固定大小的对象；固定大小场景下答案几乎总是"预分配一大块内存 + free list 链表 + O(1) 摘取/挂回"。
4. 遇到"为什么这段代码/这个数据结构慢"类问题，先问自己：这段代码的访问模式是什么（顺序 vs 随机、单字段批量 vs 多字段整体），再判断是 AoS/SoA 布局问题、预取失效问题，还是 TLB miss 问题，三者经常同时出现但成因不同。
5. 遇到"要不要开大页"类问题，先确认工作集大小和访问模式是否真的会造成大量 TLB miss，而不是默认"开大页总是更快"。
```

## 1. 内存分配器的性能开销来源

**核心结论**：Linux 下默认的 `malloc`/`free`（glibc 的 ptmalloc2）是一个通用分配器，设计目标是"对任意使用模式都能给出还过得去的表现"，为此做了不少保守的权衡。当程序的访存模式变成"高频、小对象、多线程并发"时，这些保守设计的代价会被显著放大，集中体现在三类开销上。

**全局锁竞争**：堆的元数据（各个 free 链表、bin 数组等）是进程内所有线程共享的一份数据结构，多个线程同时调用 `malloc`/`free` 时，必须对这份共享状态加锁，防止两个线程同时修改同一条空闲链表导致堆结构被破坏。ptmalloc2 引入了多 arena 机制，让不同线程尽量绑定到不同的 arena 上以缓解竞争，但 arena 数量有限（默认上限通常是 CPU 核数的若干倍），线程数远多于 arena 数时，多个线程仍然会争抢同一个 arena 的锁；而且 arena 之间彼此独立、不共享空闲内存，反而会带来额外的碎片。

**内存碎片（fragmentation）**：可以分成两类。**外部碎片**指空闲内存总量足够，但分散成许多不连续的小块，无法满足一次稍大的分配请求；**内部碎片**指分配器为了实现方便，把请求"打包"进一个略大的预设尺寸块里，块内用不满的部分被浪费掉。长期运行、反复分配释放不同大小对象的服务，堆会随时间推移变得越来越破碎，表现为常驻内存（RSS）只增不减——即使这些内存在逻辑上早就被程序释放了。这也是很多被误诊为"内存泄露"的问题，实际根源是碎片化而不是真正丢失了引用。

**系统调用开销**：分配器自己维护的空闲内存不够用时，需要通过 `brk`（扩展堆顶）或 `mmap`（映射一块新的虚拟内存区域）向操作系统申请新内存，这是一次用户态到内核态的切换，开销比纯用户态的函数调用高出一到两个数量级。如果每次分配都触发一次系统调用，性能会非常差，因此任何一个像样的分配器都会在用户态维护一层缓存，把大部分请求挡在用户态解决，只在缓存耗尽时才真正触发系统调用——这正是第 2 节高性能分配器设计的直接动机。

**常见追问 / 面试陷阱**

> 追问"怎么区分内存泄露和内存碎片"：内存泄露是"该释放的引用没释放"，用 Valgrind/ASan 能定位到具体的未释放分配点；内存碎片是"内存确实都释放了，但分配器手里的空闲块太零散，无法复用"，表现是 RSS 持续增长但找不到对应的未释放分配点。区分的关键是看分配器自身的统计信息（比如 glibc 的 `malloc_stats()`、jemalloc 的 `jemalloc_stats_print`）里空闲内存总量和实际占用内存的比例，而不是只看进程 RSS。

## 2. 高性能分配器的核心思想：以 tcmalloc、jemalloc 为例

**核心结论**：tcmalloc（Thread-Caching Malloc）和 jemalloc 解决第 1 节三类开销的核心武器是"线程本地缓存"和"按大小分级"，把绝大多数分配路径变成不需要跨线程同步的纯本地操作，并把不可控的外部碎片问题转化为可控、可预测的内部碎片问题。

**思路一：线程本地缓存（thread-local cache）**。每个线程维护一份只属于自己的空闲内存缓存，不与其他线程共享，因此访问它不需要加锁。tcmalloc 里这个结构叫 ThreadCache：为每一个 size class 各维护一条单向空闲链表；分配小对象时先查本线程 ThreadCache 里对应尺寸档位的链表，有空闲块就直接摘下返回，整个过程是纯用户态指针操作，既没有系统调用也没有跨线程同步指令。只有当某个线程本地某个尺寸档位的链表耗尽（或者积压超过阈值需要归还），才会访问所有线程共享的 CentralFreeList，这一步才需要加锁；但由于绝大多数分配请求都能在 ThreadCache 这一级被满足，实际落到全局锁上的比例很低。jemalloc 走得更远，把整个堆切分成若干个独立的 arena，线程首次分配时按 round-robin 之类的策略被绑定到某个 arena，同一 arena 内的线程共享该 arena 自己的 tcache 和数据结构，不同 arena 之间几乎不需要同步，锁竞争被进一步摊薄到 arena 数量这个维度上。

```text
线程 1                    线程 2                    线程 N
┌───────────────┐        ┌───────────────┐        ┌───────────────┐
│ ThreadCache 1  │        │ ThreadCache 2  │  ...   │ ThreadCache N  │
│ size 8:  ●→●   │        │ size 8:  ●     │        │ size 8:  (空)  │
│ size 16: ●→●→● │        │ size 16: ●→●   │        │ size 16: ●     │
│ size 32: ●     │        │ size 32: (空)  │        │ size 32: ●→●   │
└────────┬───────┘        └────────┬───────┘        └────────┬───────┘
         │  本地缓存耗尽 / 需要归还时才访问下一层
         ▼                         ▼                         ▼
                ┌─────────────────────────────────────┐
                │  CentralFreeList（全局共享，需要加锁）    │
                │  按 size class 组织，供各线程批量取/还     │
                └───────────────────┬───────────────────┘
                                     │ 页级别空闲也不足时
                                     ▼
                ┌─────────────────────────────────────┐
                │  Page Heap（以页为单位管理更大块内存）      │
                └───────────────────┬───────────────────┘
                                     │ 向 OS 申请
                                     ▼
                            mmap / brk（系统调用）
```

**思路二：按大小分级（size class）**。分配器预先定义好一系列固定的尺寸档位（比如 8、16、32、48、64 字节……越往大档位间距越宽），任何一次分配请求都会被向上取整到最近的档位。tcmalloc 对不超过 256KB 的小对象划分出大约 80 多个 size class；jemalloc 的小对象分级更细，按固定比例递增（大致每翻一倍划出约 4 个档位），把内部碎片率的上限控制在一个可预期的比例（约 20% 左右）。分级带来的收益是：同一档位的内存块大小完全一致，任何一个刚被释放的块都能立即服务下一个请求同一档位大小的分配，不需要像通用分配器那样在不同大小的空闲块之间做合并、切分、最佳适配搜索，分配和释放都退化成链表的 $O(1)$ 头部操作。代价是"向上取整"必然造成一定比例的内部碎片（比如 12 字节的请求被塞进 16 字节档位，浪费 4 字节），但这种浪费的比例是可分析、可控的，工程上远比无法预测何时会耗尽的外部碎片更容易接受。

**大对象走独立路径**：以上两个机制主要为小对象设计，因为小对象分配频率极高，复用同一档位空闲块的收益也最大。超过某个阈值（不同实现门槛不同，量级通常在几十 KB 到几百 KB，比如 tcmalloc 以 256KB 为界）的大对象，分配次数本身少得多，把它们也塞进固定档位反而可能造成大量浪费的内部碎片，因此大对象分配通常绕开 ThreadCache/size class 这一整套机制，直接在 Page Heap 一级按页分配，或者干脆直接调用 `mmap` 向操作系统申请一整块专用的虚拟内存，用完后也直接 `munmap` 归还，不经过任何缓存层。

| 维度 | tcmalloc | jemalloc |
|---|---|---|
| 线程本地结构 | ThreadCache（每线程一份，含每 size class 一条空闲链表） | tcache（绑定到线程当前所属的 arena） |
| 共享堆划分 | 主要靠 ThreadCache 摊薄 + 单一 CentralFreeList | 划分为多个独立 arena，线程分摊到不同 arena，天然降低竞争面 |
| 小对象 size class 数量 | 约 80 余档 | small/large/huge 三段，small 内部按约 4 档一倍的比例递增 |
| 大对象处理 | 超过阈值直接走 Page Heap / `mmap` | 划出 large、huge 独立类别，各自走不同的元数据管理路径 |
| 典型优势场景 | 高并发多线程程序里小对象分配密集的场景 | 更强调降低碎片率与 NUMA 感知，适合长时间运行、内存敏感的服务 |

**常见追问 / 面试陷阱**

> 追问"为什么不干脆让所有线程共享一个无锁队列，而要用线程本地缓存"：无锁队列本身仍然需要 CAS 之类的原子操作，在高竞争下会因为反复重试而退化到接近锁的开销；而线程本地缓存在没有耗尽之前完全不产生任何跨线程可见的同步指令，是真正意义上的零竞争，只有在少数需要和中心结构交互的时刻才付出一次同步代价。

> 追问"为什么内部碎片可以接受，外部碎片要极力避免"：内部碎片的浪费比例是有上界、可分析的（比如 jemalloc 控制在约 20%），不会随时间无限恶化；外部碎片没有这个性质，长期运行下空闲内存可能碎成大量无法拼凑出一次完整分配的小块，即使总空闲量看起来充足，也可能触发分配失败，风险不可控。

## 3. 内存池（memory pool）自实现思想

**核心结论**：内存池的动机是把"频繁分配/释放大小相近对象"这一类特定场景的先验知识，从通用分配器手里收回到应用层：如果应用明确知道自己会反复创建、销毁大量同类型对象（游戏引擎里的粒子、网络服务器里的连接、撮合引擎里的订单节点），完全可以自己预先申请一大块连续内存，自己管理这块内存的分配和回收，彻底绕开通用分配器的 size class 查找、跨线程同步等通用性开销，把每次分配/释放压到"从链表摘一个节点/挂一个节点"这个量级。

固定大小对象内存池的核心结构是一条**空闲链表（free list）**：预分配的整块内存被切成大小相等的槽位，未使用的槽位串成一条单向链表；分配时从链表头部摘下一个槽位返回，释放时把归还的槽位重新挂回链表头部，两个操作都是 $O(1)$，且不涉及遍历、合并、查表。

```cpp
template <typename T>
class MemoryPool {
public:
    explicit MemoryPool(size_t capacity)
        : pool_(::operator new(capacity * sizeof(Slot))),
          capacity_(capacity) {
        // 把预分配的大块内存切成 capacity_ 个槽位，串成一条 free list
        Slot* slots = static_cast<Slot*>(pool_);
        for (size_t i = 0; i + 1 < capacity_; ++i) {
            slots[i].next = &slots[i + 1];
        }
        slots[capacity_ - 1].next = nullptr;
        free_list_ = slots;
    }

    ~MemoryPool() {
        ::operator delete(pool_);
    }

    // 分配：O(1)，从 free list 头部摘一个槽位
    T* allocate() {
        if (!free_list_) {
            throw std::bad_alloc(); // 简化实现：池耗尽即失败，不做自动扩容
        }
        Slot* slot = free_list_;
        free_list_ = free_list_->next;
        return reinterpret_cast<T*>(slot);
    }

    // 释放：O(1)，把槽位重新挂回 free list 头部
    void deallocate(T* ptr) {
        Slot* slot = reinterpret_cast<Slot*>(ptr);
        slot->next = free_list_;
        free_list_ = slot;
    }

private:
    union Slot {
        Slot* next;                                    // 槽位空闲时，借用这块内存存"下一个空闲槽位"的地址
        alignas(T) unsigned char storage[sizeof(T)];   // 槽位被占用时，存放实际的 T 对象
    };

    void* pool_;
    size_t capacity_;
    Slot* free_list_ = nullptr;
};
```

`Slot` 用 `union` 是这个实现里最容易被追问的细节：一个槽位在"空闲"和"被占用"这两个状态下从不同时需要两份数据，空闲时它本来没有任何有效内容，正好借用这块内存自己的空间存"下一个空闲槽位的地址"，链表结构直接寄生在被管理的空闲内存内部，不需要额外的元数据开销。

```text
初始状态（free_list_ 指向 slot0，四个槽位依次链接）：

free_list_ ──▶ [slot0] ──▶ [slot1] ──▶ [slot2] ──▶ [slot3] ──▶ nullptr

allocate() 一次后（摘下 slot0，交给应用层使用）：

free_list_ ──▶ [slot1] ──▶ [slot2] ──▶ [slot3] ──▶ nullptr
               [slot0] 已被使用，暂时不在链表上

deallocate(slot0) 后（重新挂回链表头部）：

free_list_ ──▶ [slot0] ──▶ [slot1] ──▶ [slot2] ──▶ [slot3] ──▶ nullptr
```

这个简化实现有几个明显的局限，面试里经常被追问：只管理单一固定大小的对象，不是通用分配器；没有线程安全保护，多线程场景需要加锁或者换成无锁栈；池耗尽后直接抛异常，工程实现通常会按"块（chunk）"为单位做二次扩容——申请一整块新内存，同样切成槽位链接进现有 free list，这也是 tcmalloc 的 CentralFreeList 向 Page Heap 申请新页时使用的同一套思路。

**常见追问 / 面试陷阱**

> 追问"内存池和 tcmalloc/jemalloc 的线程本地缓存本质上是不是一回事"：核心思想相同——预先攒一批同尺寸空闲块，用链表管理，分配/释放都是 $O(1)$ 的头部操作。区别在于内存池是应用层针对某一种具体业务对象类型定制的，不需要处理"任意大小、任意类型"的通用性，可以做得更极致（比如完全不用考虑多档 size class、不用考虑归还给其他线程）；而 tcmalloc/jemalloc 要在保持通用性的前提下逼近内存池的效果，因此多了一层 size class 分级和跨线程归还的机制。

## 4. 数据结构的内存局部性：AoS vs SoA

**核心结论**：AoS（Array of Structures，结构体数组）把同一个对象的所有字段存在一起，适合"一次性整体访问一个对象的多个字段"的模式；SoA（Structure of Arrays，数组的结构体）把同一个字段在所有对象上的值连续排列，适合"批量只访问所有对象的某一个字段"的模式。这不是"SoA 天生更快"，而是缓存行（cache line）有效利用率随访问模式变化的直接结果——本质上是访问模式决定最优布局的取舍问题。

```cpp
// AoS：结构体数组
struct ParticleAoS { float x, y, z, mass; }; // 16 字节
std::vector<ParticleAoS> particles(N);

float sumX_AoS() {
    float sum = 0;
    for (auto& p : particles) sum += p.x; // 每次有效访问只有 x，但 y/z/mass 也被一起载入 cache
    return sum;
}

// SoA：数组的结构体
struct ParticlesSoA {
    std::vector<float> xs, ys, zs, masses; // 各自独立、内部连续
};
ParticlesSoA soa; // 四个数组各自 resize(N)

float sumX_SoA() {
    float sum = 0;
    for (float x : soa.xs) sum += x; // 载入的每一个字节都是这次运算需要的数据
    return sum;
}
```

```text
AoS 内存排布（每个 Particle 16 字节，内存地址增长方向 →）：

[x0 y0 z0 m0][x1 y1 z1 m1][x2 y2 z2 m2][x3 y3 z3 m3]
 └──16字节──┘ └──16字节──┘ └──16字节──┘ └──16字节──┘

一条 64 字节 cache line 恰好装下 4 个 Particle；只遍历 x 时，
真正用到的数据是 x0,x1,x2,x3 共 16 字节，其余 y/z/mass 共 48
字节被一起载入却完全没用到，有效利用率 16/64 = 25%。

SoA 内存排布：

xs:     [x0][x1][x2][x3][x4][x5][x6][x7]...  ← 连续排列
ys:     [y0][y1][y2][y3][y4][y5][y6][y7]...
zs:     [z0][z1][z2][z3][z4][z5][z6][z7]...
masses: [m0][m1][m2][m3][m4][m5][m6][m7]...

只遍历 xs 时，一条 64 字节 cache line 能装下 16 个连续的 float，
全部都是本次运算需要的数据，有效利用率接近 100%。
```

反过来的场景同样重要：如果访问模式是"每次都要同时用到一个粒子的 `x,y,z,mass` 一起做计算"（比如按时间步更新每个粒子的位置，需要同时读 `x,y,z,mass` 并写回 `x,y,z`），AoS 反而更合适——一次 cache line 加载就能拿到这个对象几乎所有需要的字段；而 SoA 布局下同一次更新需要分别访问四个独立数组里相隔很远的地址，产生四条独立的内存访问流，实际的 cache/TLB 压力可能比 AoS 更大。

工程上还存在折中方案 **AoSoA（Array of Structures of Arrays）**：把对象按固定数量（比如 8 个或 16 个，通常匹配 SIMD 向量宽度）打包成一个小的 SoA 块，再把这些块排成数组，试图同时兼顾"批量单字段访问的缓存效率"和"SIMD 向量化所需的对齐、连续内存"，是游戏引擎和科学计算库里常见的进一步优化，这里只需要知道这个概念的存在和动机。

**常见追问 / 面试陷阱**

> 追问"这和之前讲的 `struct` 内存对齐/padding 有什么关系"：对齐/padding 决定的是单个对象内部字段的相对偏移和整体大小，AoS/SoA 讨论的是多个对象之间在内存里如何排布，二者是不同层面的问题，但会叠加影响：AoS 下如果单个对象因为 padding 变大，会进一步拉低批量单字段访问时的 cache line 利用率。

> 追问"如果一部分字段需要批量访问、另一部分字段需要整体访问，应该怎么设计"：可以按访问频率把字段拆成"热字段"和"冷字段"两个结构体分别存放（hot/cold field splitting），热路径只遍历热字段所在的紧凑数组，冷字段单独存放不参与热路径的批量扫描，这是 SoA 思路的一种局部化应用，不要求整个对象要么全 AoS 要么全 SoA。

## 5. 硬件预取（prefetching）

**核心结论**：现代 CPU 在硬件层面内置了预取器（prefetcher），持续监控最近的访存地址序列，一旦识别出规律性的模式，就主动把预测到的未来会被访问的地址提前加载进 cache，在程序真正执行到对应的加载指令之前就把数据准备好，从而把原本会暴露给程序的内存访问延迟隐藏掉。

**预取器能识别的模式不止"步长为 1"的顺序访问**：最基础的流式（stream）预取器识别连续递增、步长恰好是一个 cache line 的访问；更进一步的 stride 预取器会记录最近几次访存地址之间的差值（stride），如果连续观察到几次相同的步长，就认定存在一个稳定的跨步访问模式，进而按这个固定步长提前预取后续地址——这意味着按固定间隔跳跃访问（比如按列遍历一个按行存储的矩阵）也有机会被预取器覆盖，不是只有严格连续访问才能享受预取收益。跨步预取的检测复杂度显著高于纯顺序预取，能覆盖的步长范围、能同时跟踪的独立访问流数量在不同微架构上有不同的硬件限制。

**预取失效的情况**：一旦访问模式变成真正的跳跃式、且下一个地址依赖运行时才能算出的结果（典型的"指针追逐"，pointer chasing，比如遍历链表——必须先解引用当前节点才能知道下一个节点在哪），预取器完全无法提前预测下一个地址，退化成每次访问都要实打实地等待一次完整的内存延迟。这正是"遍历数组通常比遍历链表快得多"的第二个原因，除了教科书里常提到的"减少指针解引用次数"之外：数组访问是连续、可预测的，预取器能提前把后续元素成批搬进 cache；链表节点由于是多次独立分配得到的，物理地址往往彼此相距很远，几乎不可预取，每一次跳转都完整暴露了内存延迟。

**常见追问 / 面试陷阱**

> 追问"预取器预测错了会有什么后果"：一次错误的预取只是把不会被用到的数据提前搬进了 cache，浪费一部分内存带宽，还可能顶替掉本来有用的数据造成 cache 污染，但不会导致程序结果错误——程序真正需要的数据仍然会在需要时被正常读取（如果预取的地址错了，这次访问依然是一次正常的、未命中的内存访问）。预取器只影响性能，不影响正确性。

## 6. TLB 与大页（huge pages）

**核心结论**：虚拟地址到物理地址的翻译需要查页表（page table），页表本身也存放在内存里，如果每次访存都真的走一遍多级页表查询会非常慢，因此 CPU 专门内置了一块高速缓存——**TLB（Translation Lookaside Buffer）**——缓存最近用过的"虚拟页 → 物理页"映射关系。TLB 命中时地址翻译只需要一次 cache 级别的查找（通常 1 个周期左右）；未命中时才需要真正执行一次完整的多级页表查询，称为 **page walk**，x86-64 的四级页表在最坏情况下需要多达 4 次真实的内存访问才能完成一次翻译，代价远高于一次 TLB 命中。

```text
CPU 发出一次虚拟地址访存请求
        │
        ▼
   查 L1 DTLB（典型规模几十~100 出头个 entry，约 1 周期延迟）
        │
   ┌────┴────┐
命中│         │未命中
   ▼          ▼
直接得到    查 L2 STLB（统一/共享，典型规模上千个 entry，几个周期延迟）
物理地址        │
              ┌─┴──┐
          命中│    │未命中
              ▼     ▼
          得到物理  触发 page walk：
          地址      依次查 PML4 → PDPT → PD → PT（四级页表）
                    最坏情况 4 次真实内存访问，结果写回 TLB
```

**TLB 容量有限带来的问题**：以典型 x86-64 微架构为例，L1 DTLB 通常只有几十到 100 出头个 entry（对应 4KB 页粒度），L2 STLB 通常是 1000 到 2000 出头个 entry。按 Linux 默认的 4KB 页大小计算，L1 DTLB 能覆盖的工作集（working set）大约只有几百 KB，L2 STLB 也大致只能覆盖几十 MB 量级。如果一个进程实际频繁访问的内存范围远超过这个覆盖范围——比如一个几 GB 大小、访问模式接近随机的哈希表或内存数据库——大部分访存都会发生 TLB miss，需要走一次昂贵的 page walk，这在访存密集型程序里可能占到总执行时间相当可观的比例。

**大页的作用**：把单页大小从默认的 4KB 提升到 2MB 甚至 1GB（x86-64 同时支持这两档大页），同样数量的 TLB entry 能覆盖的内存范围随之扩大几百倍到几十万倍（一个 2MB 页相当于 512 个 4KB 页），同一个工作集需要覆盖的页数量大幅减少，TLB miss 率相应大幅下降。代价是页粒度变粗后，如果实际使用的内存范围没有对齐、填满整个大页，会造成更明显的内部碎片（哪怕一个 2MB 大页只用到 4KB，也要整页占用），因此大页更适合内存工作集本身很大、访问密集、内存利用率高的场景（数据库、大规模内存计算、虚拟机宿主），不适合大量小对象、生命周期琐碎的通用分配场景。

Linux 提供两种使用大页的方式：**THP（Transparent Huge Pages）**由内核在后台自动尝试把连续的匿名内存合并成大页，应用不需要改代码，但合并/拆分动作本身有额外开销，在某些延迟敏感的工作负载下反而可能引入延迟毛刺（这也是不少数据库、低延迟交易系统选择关闭 THP、转而显式管理大页的原因）；**hugetlbfs** 是显式方案，需要预先在系统层面保留一批大页，应用通过挂载的 hugetlbfs 文件系统或 `mmap` 配合 `MAP_HUGETLB` 标志显式申请，行为完全可预测，代价是需要额外的运维配置和代码改动。

**常见追问 / 面试陷阱**

> 追问"开大页是不是总能提升性能"：不是。如果工作集本身很小，远小于默认页 TLB 能覆盖的范围，开大页几乎没有收益，反而可能因为内部碎片增加实际内存占用；大页真正的收益只出现在"工作集很大、TLB miss 确实是瓶颈"的场景下。使用前应该先用 profiling 工具（比如 `perf` 的 `dTLB-load-misses` 事件）确认 TLB miss 确实是当前瓶颈，而不是想当然地默认开启。
