# 数据、样本与特征流

## 第 2 章 数据、样本与特征流

训练表来自三类原始记录：线上请求、每层候选轨迹和延迟到达的用户反馈。先把它们按时间与版本对齐，后面才谈得上召回 pair、曝光样本或列表偏好。

### 2.1 请求是所有数据的主键

同一次请求会经过多个服务。`request_id` 要贯穿 query 理解、召回、排序、重排和曝光，才能还原一件物品在哪一层进入、在哪一层被删掉。

推荐请求常见字段：

```text
request_id, user_id, session_id
scene, timestamp, device, region
recent_actions
experiment_ids
```

搜索还需要：

```text
raw_query, normalized_query
query_intent, filters
rewrite_source
```

用户画像和历史序列不宜整份复制进每条日志。日志记录快照版本或 feature key，需要时再按 point-in-time join 还原。

### 2.2 候选轨迹要能逐层回放

只记最终曝光不够。召回调优需要知道每个候选来自哪一路，粗排需要知道哪些候选被提前误杀，规则排障需要保存过滤原因。

一条候选轨迹至少包含：

| 字段 | 用途 |
| --- | --- |
| `request_id, item_id` | 连接一次请求中的同一候选 |
| `stage, channel` | 标记召回、粗排、精排、重排及召回来源 |
| `raw_score, calibrated_score` | 回放模型分数和融合过程 |
| `rank_before, rank_after` | 观察每一层怎样改变位置 |
| `filter_reason` | 区分库存、安全、已看、配额等删除原因 |
| `model/index/rule_version` | 定位发布与版本错配 |
| `event_time` | 保证时间切分和特征回放 |

全量保存每层所有候选可能太贵，可以对中间轨迹采样；最终曝光、关键过滤和实验流量应保留完整记录。

### 2.3 反馈要按时间成熟

曝光后很快能观察点击，购买、退款和次日留存要等更久：

```text
t0 请求与曝光
t1 点击 / 跳过
t2 加购 / 播放完成
t3 下单
t4 退款或留存窗口结束
```

训练样本要声明标签截止时间。例如预测 7 日购买，今天的曝光不能明天就当负例。常见做法是只使用已经过成熟窗口的样本，或对尚未成熟的标签单独建模。

行为强度也不能混成一个 `label`。点击、有效播放、点赞、购买和举报有不同含义；后面的多目标模型会分别消费这些字段。

### 2.4 未点击不自动等于负样本

用户只能反馈系统展示过的内容。未召回 item 没有观察标签，曝光未点击也可能因为位置太低、页面没滚到或网络中断。

需要保留几类偏差：

- 选择偏差：旧召回与排序策略决定了谁能进入日志；
- 位置偏差：头部候选天然获得更多交互；
- 热门偏差：高曝光继续积累更多正反馈；
- 生存者偏差：被规则提前过滤的内容从训练集消失；
- 延迟反馈：标签尚未成熟就被误记为负例。

随机曝光、探索桶、propensity weighting 和延迟修正可以缓解部分问题。负采样只改变训练分布，无法凭空补出从未展示候选的真实反馈。

### 2.5 各阶段需要不同样本

| 模块 | 一条训练样本 | 常见正例 | 候选或负例 |
| --- | --- | --- | --- |
| 协同召回 | 用户历史与下一个 item | 点击、有效播放、购买 | 全库采样、批内或 hard negative |
| 搜索召回 | query 与 document/item | 人工相关或高质量交互 | BM25/旧模型召回的难例 |
| 精排 | 一次曝光中的 user/query-item | 点击、时长、转化 | 同次曝光未互动候选 |
| 列表模型 | 请求与完整 slate | 列表级反馈 | 其他排列或策略生成列表 |
| 生成式推荐 | 历史序列与 item/SID 序列 | 下一 item 或偏好列表 | 词表竞争者、rejected、rollout |

同一条用户行为可以进入多个任务，但样本单位不同。把召回 pair、精排曝光样本和列表偏好对混在一张表里，通常会丢掉候选来源与列表上下文。

### 2.6 特征按可用时间拼接

特征大致分为四组：

- 用户：长期画像、近期行为、活跃度；
- query 或场景：词项、意图、时间、地域、入口；
- item/doc：内容、类目、作者、质量、库存；
- 交叉：用户对类目的历史偏好、query-item 文本匹配、上下文中的实时统计。

训练时只能读取事件发生前已经存在的值。若用当天最终销量预测当天早上的点击，就发生了时间穿越。可靠的特征平台要支持 point-in-time join，并记录特征生成时间、schema 和默认值。

线上缺失处理也要与训练一致。训练中删除缺失样本，服务时却填零，会让模型上线后看到新的输入分布。

### 2.7 大规模稀疏 Embedding 基础设施 (Large-Scale Embedding Systems)

工业级推荐系统的特征具有极端的异质性（Heterogeneity）：
- **稀疏 Embedding 侧 (Memory-Bound)**：用户 ID、物品 ID、Query、历史交互序列等离散特征基数达数百亿，参数量高达数百 GB 至数 TB。计算量极小（仅查表与 Pooling），但显存根本无法容纳；
- **稠密 MLP 侧 (Compute-Bound)**：前向多层全连接与注意力参数量仅数 MB 至数百 MB，矩阵乘法密集，极度契合 GPU 计算。

#### 1. 混合并行：参数服务器 (PS) 与 GPU Table Sharding
为了支撑 TB 级稀疏模型，工业推荐系统（如 Meta DLRM、字节 Monolith、阿里 WDL）采用**模型并行 + 数据并行**的混合并行架构：
- **模型并行 (Table Sharding)**：超大 Embedding 表按特征 ID 分片（Hash Sharding 或按特征域划分）离散存储在跨节点的 CPU 内存池（Parameter Server）或大显存 GPU 集群中；
- **数据并行 (Data Parallelism)**：所有计算节点各自复制一份相同的 Dense MLP 网络，接收不同的 Data Batch 进行并行梯度反向传播；
- **All-to-All 集合通信瓶颈**：各个 GPU 节点先从本地或远程分片拉取各自样本所需的 Embedding 向量，随后必须通过跨节点的 `All-to-All` 全局集合通信算子（基于 NVLink / RoCE），将散落在不同机器上的 Embedding 特征重排并汇聚到对应的 Dense Worker。

#### 2. TB 级动态特征准入与淘汰 (Dynamic Admission & Eviction)
内存不可能无上限容纳所有历史 ID，必须通过在线准入与淘汰保证内存恒定并抑制过拟合：
- **特征准入控制 (Admission Control)**：
  - 绝大多数长尾 ID（如只出现一次的冷门商品或小号）属于噪声，为其分配 Embedding 会引发显存爆炸并严重过拟合；
  - 采用 **Bloom Filter** 或 **Count-Min Sketch** 统计滑动窗口内特征的出现频次；
  - 仅当特征出现频次超过阈值（如 $k \ge 5$ 次）时，系统才正式在持久化内存中为其初始化分配 Embedding 向量。
- **特征淘汰策略 (Eviction Policy)**：
  - 结合 **$L_2$ 权重衰减 (Weight Decay)**：长期未被访问的陈旧特征向量，其权重范数随时间推移逐渐衰减趋近于 0；
  - 后台异步运行 **LRU / LFU 淘汰扫描**，定期释放长期未更新且范数极小的冷门特征内存（如 ByteDance Monolith 的无冲突动态特征表），将内存占用压制在固定 SLA 上限内。

### 2.8 数据集按时间切分

推荐与搜索日志有明显时间顺序。随机打散会让未来热门 item、后续用户行为或新版特征泄漏进训练集。

```text
训练窗口        验证窗口       测试窗口
──────────────|───────────|───────────>
              冻结特征和样本构造版本
```

每次实验应能回答：用了哪段日志、标签何时成熟、负样本怎样采、特征快照是哪版、候选由哪个策略产生。没有这些信息，离线结果很难复现。

### 2.9 本章自测

1. 为什么 `request_id` 必须贯穿整条在线链路？
2. 只记录最终曝光会漏掉哪些召回和粗排问题？
3. 7 日转化标签为什么需要成熟窗口？
4. 为什么大规模推荐模型需要采用“Embedding 模型并行 + MLP 数据并行”的混合架构？
5. 动态特征准入 (Admission) 与淘汰 (Eviction) 解决了什么核心工程问题？
6. point-in-time join 解决什么问题？

<details>
<summary>参考答案</summary>

1. 它把请求、各阶段候选、最终曝光和延迟反馈连接成一次可回放事件；缺失后无法判断候选在哪一层进入或被过滤。
2. 会丢掉召回通道、粗排误杀、过滤原因和阶段排名变化，只能看到幸存候选，无法定位漏斗损失。
3. 窗口结束前尚未购买的样本仍可能在第 2–7 天转化。过早标负会制造系统性假负例。
4. 稀疏 Embedding 表参数达 TB 级，显存无法放下，且计算量小、内存吞吐受限，必须用模型并行按表分片；稠密 MLP 参数量小但计算密集，必须用数据并行利用 GPU Tensor Core 加速。两者通过 All-to-All 集合通信完成特征拼接。
5. 避免内存 OOM 并防止长尾低频噪声 ID 导致的过拟合。通过 Bloom Filter 过滤只出现一两次的低频特征，通过 L2 权重衰减与 LRU/LFU 定期淘汰陈旧冷门特征。
6. 它保证训练样本只读取事件发生时已经存在的特征，防止未来销量、后续行为或新版画像泄漏进历史样本。
