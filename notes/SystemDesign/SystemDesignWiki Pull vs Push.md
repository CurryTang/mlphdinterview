## 1 · 核心定义：推模型与拉模型

在分布式数据流与通信体系中，系统面对多端消费与状态同步存在两条根本对立的演进路径：

* **Push 模型（推 / 写扩散 / Fan-out on Write）**：当数据产生或状态变更时，由发布端主动将数据投递、复制或推送到所有订阅者的存储箱或在线连接中。
* **Pull 模型（拉 / 读扩散 / Fan-out on Read）**：当数据产生时仅原地持久化；消费端在真正需要数据时，主动发起请求进行远端查询、批量拉取并在内存中计算聚合。

## 2 · 场景一：社交 Timeline 与 Feed 流架构

Feed 流系统在处理“用户发帖”与“关注者拉流”时，推拉模型体现为典型的存储放大与计算延迟博弈：

### 2.1 · 写扩散 (Push to Inbox)
* **执行路径**：用户发帖 $\to$ 系统异步查出该用户的所有关注者列表 $\to$ 为每一个粉丝的个人收件箱（Timeline Cache）写入一份帖子索引。
* **优势**：**极度偏向读端性能**。粉丝打开客户端时，直接读取自身收件箱列表，单次读操作复杂度仅为 $O(1)$，无跨表复杂聚合，P99 延迟稳定在毫秒级。
* **缺陷与瓶颈**：**写放大严重（Write Amplification）**。一个拥有 5,000 万粉丝的大 V 发帖，单次写入瞬间被放大为 5,000 万次 Redis/DB 写操作，直接造成消息队列积压与数据库写入洪峰。此外，对于从未上线查看的“僵尸/冷用户”，写扩散生成的预聚合数据是完全的计算与存储浪费。

### 2.2 · 读扩散 (Pull from Outbox)
* **执行路径**：用户发帖 $\to$ 仅将帖子写入自己的发件箱（Outbox），写操作开销仅为 $O(1)$；粉丝刷新 Feed $\to$ 实时查询自身关注列表（$K$ 个用户） $\to$ 并发拉取这 $K$ 个用户的最新帖子 $\to$ 在内存中执行多路归并排序并分页返回。
* **优势**：**写端极其廉价且轻量**。彻底消除大 V 发帖引发的写风暴；对冷用户零额外存储开销。
* **缺陷与瓶颈**：**读端计算高昂且不可控**。读操作从单点查询退化为复杂的分布式聚合（Scatter-Gather），复杂度为 $O(K \log K)$。若关注数较多或并发请求激增，数据库与缓存面临巨大的网络带宽与算力压力，读延迟显著拉长。

### 2.3 · 工业级折中：推拉结合的混合架构 (Hybrid Fan-out)
现代大规模社交平台（如微博、Twitter）均采用基于**用户粉丝量阈值**的动静解耦混合策略：
* **普通用户（粉丝数 $< 10^4$）**：发帖采用 **Push（写扩散）**，直接注入粉丝收件箱。
* **大 V / 明星用户（粉丝数 $\ge 10^4$）**：发帖仅写个人 Outbox，**禁止触发写扩散**。
* **读端聚合逻辑**：普通用户刷新 Feed 时，并行执行两项动作：
  1. 读取自身个人收件箱（已包含普通好友推送的内容）；
  2. 针对自己关注列表中的少量大 V，并发 Pull 其 Outbox 动态；
  3. 在应用层内存中完成轻量级并集归并（通常只需合并 5~10 个大 V 的预热缓存）。

## 3 · 场景二：客户端与服务端通信 / 数据同步

在客户端获取实时事件（如即时消息、通知、大模型流式生成）时，推拉模型决定了网络层与连接管理的设计：

| 机制 | 模式 | 运作原理 | 适用场景与工程代价 |
|---|---|---|---|
| **短轮询 (Short Polling)** | Pull | 客户端每隔固定时间（如 5s）发送一次标准 HTTP 请求。 | **实现极简、无状态、天然适配 CDN 缓存**；但绝大多数请求为空轮询，无效吞吐高，产生大量连接开销与网络带宽浪费。 |
| **长轮询 (Long Polling)** | Pull | 客户端发送 HTTP 请求，若无新数据，服务端将连接挂起直到超时（如 30s）或有新事件到达才返回。 | 实时性显著优于短轮询，连接仍保持无状态特性；但在事件高频到达时仍存在持续重连与 HTTP 头传输冗余。 |
| **WebSocket** | Push | 基于单个 TCP 连接建立全双工双向长连接通道。 | **极高实时性、超低协议报头开销、双向交互**；但网关层必须维护百万级长连接 Session 状态，需精心设计心跳保活、断线重连退避与重连风暴防御。 |
| **Server-Sent Events (SSE)** | Push | 基于标准单向 HTTP 长文本流（`text/event-stream`），由服务端持续推送文本事件。 | **轻量、天然穿透防火墙与代理、浏览器原生断线重连**；天然契合 **LLM Token 逐字流式返回** 与单向推送通知，比 WebSocket 更简单健壮。 |
| **Webhook** | Push | 事件发生时，服务端主动发起 HTTP POST 回调调用接收方注册的外部 URL。 | **服务间（B2B / 异步平台）解耦标准**；需保证调用超时重试机制与调用方签名鉴权。 |

## 4 · 选型决策矩阵与工程 Trade-offs

| 评估维度 | 优先选 Pull (读扩散 / 轮询) | 优先选 Push (写扩散 / 长连接推送) |
|---|---|---|
| **读写比例 (Read / Write Ratio)** | 写多读少（或单实体写开销敏感）。 | 读多写少（如读写比 $\ge 100:1$ 的社交平台）。 |
| **扇出规模 (Fan-out Factor)** | 单个发布者关联大量订阅者（大 V、全员广播）。 | 单个发布者仅关联少量关注者（1:1 聊天、私密好友圈）。 |
| **延迟容忍度 (Latency SLA)** | 弱实时（容忍秒级、分钟级数据滞后）。 | 强实时（毫秒级端到端响应，如交易、协作、告警）。 |
| **服务端状态与伸缩性** | 追求服务端**完全无状态**与无感知横向弹性伸缩。 | 允许服务端维护**有状态长连接**，并配套接入层分布式网关集群。 |
| **数据冷热分布** | 活跃用户占比低，冷用户长尾极其庞大。 | 用户日活高（活跃消费能完全平摊写预计算开销）。 |

### 核心权衡铁律 (The Rule of Thumb)
1. **写扩散的本质是用存储与写入峰值换取极速读性能**；当写入放大倍数超过系统边际收益时，必须果断切换为读扩散或混合架构。
2. **长连接推模式的本质是用接入层有状态内存换取网络带宽与低延迟**；对于低频交互或长尾更新，盲目上 WebSocket 只会徒增运维和宕机恢复成本，此时长轮询或轻量轮询往往更加稳健。
